# 0013: Firmware and PCI tolerance for VMware

Status: confirmed (2026-10-09; D9 added, D3 and D5 relabeled as general hardening, and the VMware evidence recorded 2026-10-10 after the Workstation Pro 26.0.1 check)
Depends on: 0014, whose `V1` profile and computed boot count the QEMU cases use. 0015a, only for the manual VMware checks (tests 14 and 16) and its VM settings doc. The code and host tests depend on nothing.
Ledger: G3a, S1, S1a, S10 (related: G3, S1b, P9)

## Goal
Mirror's boot-time platform discovery accepts the ACPI tables and PCI topology that VMware Workstation presents. On VMware a normal boot reaches xAPIC mode with every vCPU online, and the AHCI controller and e1000 NIC behind VMware's bridges are visible to driver binding. A redundant or surplus MADT record costs at most that record, and an unused table costs at most that table. An IOAPIC whose ID register disagrees with its MADT record, as VMware's always does, costs one marker line (D9). None of these sends the machine to single-CPU PIC/PIT mode. Boots without an HPET keep SMP and AHCI; 0014's `V1` NoHpet-CpuCount4 case covers them in QEMU. VMware needs the MADT capacity, PCI and IOAPIC changes (D4, D7, D9). The duplicate-NMI and HPET changes (D3, D5) are general hardening for real-hardware firmware, because VMware's firmware triggers neither.

Verified defects this spec removes:
- A type-4 wildcard local NMI (UID 0xFF) plus a type-10 wildcard (UID 0xFFFFFFFF) on the same LINT returns `Error::Duplicate` (crates/acpi/src/lib.rs:597-604). The MADT is then discarded (kernel/src/acpi.rs:139-166), which leaves no APIC, no LAPIC timer and no SMP (kernel/src/apic.rs:192, kernel/src/smp.rs:206-208). tests.rs:546 locks in a related case: a specific type-4 UID plus a type-10 wildcard. VMware does not trigger this (D3).
- More than 64 usable CPU records, or more than 64 local NMI records, returns `Error::Capacity` from `push` (lib.rs:20-23, 676-685) and discards the MADT in the same way. CPU records with neither availability bit set are already ignored (lib.rs:564-566). NMI records are not.
- The HPET parser rejects a GAS with nonzero bit width, bit offset or access size (lib.rs:185-191; tests.rs:156-163 assert that widths 32 and 64 fail). It also rejects a block ID with REV_ID 0 or bit 14 set (lib.rs:179-184). The driver additionally requires the table's block ID to equal GCAP_ID[31:0] (kernel/src/clock.rs:163). VMware does not trigger this (D5).
- `apic::prepare` rejects an IOAPIC whose ID register (bits 31:24) differs from its MADT record (kernel/src/apic.rs:242-244). The boot then keeps the legacy PIC, the PIT timer and one CPU (smp.rs:206-208). Static analysis of VMware's firmware and vmware-vmx shows that VMware always presents this mismatch (D9). So a VMware boot today logs either `MIRROR_ACPI_SKIPPED` (more than 64 CPU slots, the capacity defect above) or `MIRROR_APIC_SKIPPED reason=ioapic_id_mismatch` (64 or fewer). Observed 2026-10-11: every boot of 0015a's check 9 (1 vCPU) logged `MIRROR_APIC_SKIPPED reason=ioapic_id_mismatch`, then the PIT on the legacy PIC and `MIRROR_SMP_SKIPPED reason=legacy_pic`.
- Root-table entries are read with `?` (kernel/src/acpi.rs:118, 134-135). One unreadable entry aborts all discovery, the MADT and HPET included. So does an unused table whose header length falls outside 36 bytes to 256 KiB (lib.rs:117). `Root::parse` also rejects a null or repeated entry (lib.rs:237-244).
- The PCI inventory keeps the first 32 functions (kernel/src/pci.rs:33, 139-144), and every claim searches only those (pci.rs:231-235, 403-407, 572-574). A controller past entry 32 is reported as absent (`MIRROR_AHCI_SKIPPED reason=no_disk`, kernel/src/main.rs:861).

## Non-goals
- Interrupt robustness, which belongs to 0055 (M4): legacy-free platforms with PCAT_COMPAT=0 (apic.rs:193-195, after which timer.rs:120-122 unmasks IRQ0 on a PIC the firmware says is absent) or no PIT, LAPIC timer calibration against the HPET (timer.rs:176-199 uses only the PIT), catch-all vector handlers (which also make the BSP's missing IRR check harmless, apic.rs:221 compared with the AP path at apic.rs:567), LINT1 NMI on the boot CPU only, and x2APIC handoff (apic.rs:338-339, smp.rs:271-272). IOAPIC identity is the exception: it is changed here (D9, added 2026-10-10), because every VMware boot depends on it.
- SMP with more than 64 enabled CPUs. After D4 the MADT parses, but smp.rs:157-161 still skips SMP. No v1 VM needs that many CPUs.
- A time source other than the HPET, which belongs to 0055 (ledger S10; Open question 2, resolved). Without an HPET, SYS_CLOCK_GET returns -19 (kernel/src/userspace.rs:3146-3149), and AHCI waits are bounded only by POLL_LIMIT (kernel/src/ahci.rs:74, 654-659). 0015a's reference VMware settings enable the HPET explicitly (docs/vm-settings.md).
- The PCI device model, which belongs to 0060: BAR sizing, ECAM, MSI, several controllers of one class, and enabling decode that firmware left off (pci.rs:509-511). The e1000 driver belongs to 0070, and QEMU device profiles belong to 0014.
- General relaxation of MADT reserved-bit checks (Open question 3). Only the cases listed here change.
- Physical hardware (ledger G3). D3 and D5 make the parser tolerate firmware habits seen on real hardware, but nothing here is validated on it.

## Decisions
| ID | Decision | Status |
| --- | --- | --- |
| 0013-D1 | The tolerance target is VMware Workstation. QEMU carries the automated coverage, and VMware is checked by hand. (Amended 2026-10-09: VirtualBox dropped, G3a amended.) | confirmed (ledger G3a) |
| 0013-D2 | The controllers that must stay visible are those in the v1 device set: AHCI SATA and the e1000-family NIC. PS/2 and the UEFI framebuffer need no PCI binding. VirtIO is not a target. (Amended 2026-10-09 with S1a: the VMware SVGA II adapter joins the v1 device set and 0069 binds it; D7's 256-function retention keeps it visible. The vmmouse and the guest RPC channel use the backdoor I/O port, not PCI.) | confirmed (ledger S1, S1a) |
| 0013-D3 | Redundant local NMI records never reject the MADT. Two records match when they have the same LINT and the same target, meaning one UID (in either record type) or the wildcard. Their modes are compared after resolving "conforms" to active-high/edge, as apic.rs:313-314 does; the stored records keep their raw flags. A later matching record is dropped. It counts as merged if the modes are equal and as a conflict if they are not, and in both cases the first record wins. A UID-specific record and a wildcard on the same LINT are both kept, and the specific record applies to its CPU regardless of table order. Rationale: ACPI defines both 0xFF (type 4) and 0xFFFFFFFF (type 10) as "all processors", so firmware that emits both is describing one connection twice. A disagreement about the NMI pin's mode is not worth losing SMP. Alternatives: still reject the MADT on a real conflict; or, on a conflict, prefer the record whose encoding matches the CPU's record type. (Amended 2026-10-10: D3 is general hardening for real-hardware firmware, not a VMware requirement. VMware's EFI firmware emits only UID-specific NMI records, one per CPU slot and never a wildcard (static analysis of EFI64.ROM and EFI20-64.ROM), so it never triggers D3. D3 stays in M0 because it is small and already specified and tested.) | confirmed (2026-10-09; amended 2026-10-10) |
| 0013-D4 | MADT capacity. When there are more than MAX_CPUS (64) usable CPU records, enabled records take priority over online-capable ones, and the retained CPUs stay in table order. A UID-specific local NMI record whose UID matches no retained CPU is dropped. MAX_LOCAL_NMIS becomes 2 x MAX_CPUS + 2, so the filtered set always fits. IOAPIC overflow (more than 8) and NMI source overflow (more than 16) still reject the MADT. Every drop is counted. Rationale: surplus CPU and NMI records are safe to drop. A dropped IOAPIC would leave pins that firmware programmed unmanaged, and VMware is assumed to have one IOAPIC (Open question 1). Alternative: truncate every array, IOAPICs included. (Amended 2026-10-09: the rationale names VMware only, VirtualBox dropped.) (Amended 2026-10-10: static analysis confirms that VMware has one IOAPIC.) | confirmed (2026-10-09; amended 2026-10-10) |
| 0013-D5 | The HPET table supplies only the register address. The parser ignores GAS bit width, bit offset and access size, and it stores the Event Timer Block ID without validating it. The driver still checks REV_ID and bit 14 in the hardware register. The parser still requires the system-memory space ID and a valid address. The driver treats the hardware GCAP_ID as authoritative: a mismatch with the table's block ID is logged and is not fatal. Rationale: firmware commonly encodes width 64, and Linux checks neither field. Alternative: keep requiring the table's vendor ID (bits 31:16) to match the hardware. (Amended 2026-10-10: D5 is general hardening for real-hardware firmware, not a VMware requirement. VMware's EFI HPET table has an all-zero GAS width, offset and access size, which today's parser accepts, and its block ID is expected to be 0x8086af01 (REV_ID 1, bit 14 clear; static analysis of EFI64.ROM, EFI20-64.ROM and vmware-vmx). D5 stays in M0 because it is small and already specified and tested.) | confirmed (2026-10-09; amended 2026-10-10) |
| 0013-D6 | Root-table entries are handled one at a time. A null entry is skipped. A repeated address is visited once. An entry whose signature cannot be read is skipped with a diagnostic. Tables other than APIC and HPET are not read past their signature. Only failures of the RSDP and the root table abort discovery. MADT and HPET failures stay isolated from each other, as they are today. This deliberately reverses the fail-closed root discovery documented at readme.md:234 and in the comment at acpi.rs:112-116; this spec updates both. Rationale: an unused table must not cost the MADT. Alternative: keep failing closed on unreadable signatures, since such an entry might be a second MADT, and skip only null entries and unknown tables. | confirmed (2026-10-09) |
| 0013-D7 | PCI retention grows from 32 to 256 functions in the existing fixed array (pci.rs:33, 109). Binding, the serial listing and the console `devices` pages therefore cover every function up to 256, and `omitted` counts only functions beyond that. The inventory stays allocation-free, at about 4 KiB, in kmain's frame on the 256 KiB boot stack (boot.rs:52). Rationale: VMware's bus 0 alone has more than 32 functions (Open question 1). An allocation-free inventory also keeps the boot-smoke heap tests valid: heap.rs:680-687 (run at main.rs:214) and heap.rs:593 (run at main.rs:359) both assert an empty heap while the inventory is alive. Alternative: an unbounded heap `Vec`, which would require reworking those two heap tests. | confirmed (2026-10-09) |
| 0013-D8 | Raw MADT and HPET tables are captured from a Linux live guest on the reference VMware VM and committed as host-test fixtures in crates/acpi. The capture reads `/sys/firmware/acpi/tables/`, or uses `acpidump -b`, which also yields the XSDT. Rationale: the next strictness problem gets caught without booting a hypervisor. Alternative: synthetic fixtures only, with the manual boots as the only real-firmware check. (Amended 2026-10-09: the VirtualBox capture is dropped, G3a amended.) (Amended 2026-10-10: the slot count, the IOAPIC ID, the HPET table and the trailing ISOs depend on VMX inputs. Next to each fixture, record the .vmx `numvcpus`, `cpuid.coresPerSocket`, `vcpu.hotadd`, `virtualHW.version` and `guestOS`, and the vmware.log line "The EFI ROM is ...". `guestOS` stays `"other-64"`, because a Linux guest type adds per-guest defaults such as `acpi.apic.forcePhysical` and `hpet.counterRunningGTC`. The Linux guest boots with `apic=debug` and keeps its "IO APIC #", "register #00" and "physical APIC id" lines, the only place the IOAPIC register value shows (D9), plus `lspci -nn -vv` for the bus layout and the AHCI state (Open question 1). Capture at 1 and 4 vCPUs, as test 14 runs.) | confirmed (2026-10-09; amended 2026-10-10) |
| 0013-D9 | IOAPIC identity. When an IOAPIC's ID register (bits 31:24) differs from its MADT record, Mirror no longer rejects it (apic.rs:242-244). It uses the MADT address and GSI base, logs `MIRROR_APIC_IOAPIC_ID index=<n> firmware=<madt id> hardware=<reg id>`, and does not rewrite the register. The MADT ID stays the identity that the parser checks for duplicates (lib.rs:391-397). Linux x86-64 behaves the same way. Rationale: VMware's EFI firmware writes the MADT IOAPIC ID as the first unused CPU slot, which is at least 1, while vmware-vmx resets the ID register to 0 and no firmware module writes it (static analysis of EFI20-64.ROM, EFI64.ROM and vmware-vmx.exe in Workstation Pro 26.0.1; the first Mirror boot confirms). Without D9 every VMware boot falls back to one CPU on the legacy PIC, so test 14 cannot pass and 0018's Mirror rows would be measured on one CPU. Redirection entries address the BSP's local APIC ID (apic.rs:480), so the IOAPIC's own ID plays no part in delivery. QEMU never shows the mismatch, because its MADT ID and register are both 0. Alternatives: rewrite the register to the MADT value, which VMware stores but resets to 0 on every VM reset, so every boot would repeat the write; or defer to 0055 (M4) under Open question 1's rule for interrupt-controller findings, accepting single-CPU PIC boots on VMware until then. | confirmed (2026-10-10) |
| 0013-D10 | AHCI command completion. After a command's CI bit clears, `issue` waits, bounded by `REQUEST_NS`, for TFD's BSY and DRQ bits to clear before it judges the result, instead of rejecting a busy TFD at once (kernel/src/ahci.rs:460-462). It then checks the error bits as before. A TFD still busy at the bound fails with `InvalidTransfer`, as today. Rationale: ATA status bits are valid only once BSY clears. VMware's AHCI controller clears CI while TFD still reads 0xC0 (BSY, DRDY) for a short time, with the D2H FIS received and all 512 bytes transferred (PRDBC 512), observed 2026-10-11 by temporary diagnostics in 4 of 6 boots; today that fails the default build's sector-0 probe in most VMware boots (open question 5). Rejected alternative: keep the immediate check, which leaves the probe failing on VMware. | confirmed (Cameron, 2026-10-11) |

## Interfaces
There is no syscall or ABI change. Line numbers are at HEAD 4614249; 0014, 0010, 0029 and 0015a land first (Phase 0 order; 0015b moved to Phase 11 on 2026-10-11) and may shift them. Files touched:
- `crates/acpi/src/lib.rs`:
  - `Topology::parse` (lib.rs:340-508) walks the records in separate passes. CPU records (types 0 and 9) come first, using D4's priority, and the rest follow, so that NMI records can be matched against the retained CPUs.
  - `add_cpu` (lib.rs:561-591) truncates instead of failing in `push`. `add_local_nmi` (lib.rs:593-606) implements D3 and D4 instead of returning `Duplicate`.
  - `MAX_LOCAL_NMIS` (lib.rs:23) becomes `2 * MAX_CPUS + 2`.
  - New `pub struct MadtDiagnostics { omitted_cpus, merged_nmis, conflicting_nmis, unmatched_nmis }` (all `u32`) and `Topology::diagnostics()`.
  - `Hpet::parse` drops the checks at lib.rs:179-184 and lib.rs:191 (D5).
  - `Root::parse` (lib.rs:220-246) stops rejecting null and repeated entries, and `addresses()` (lib.rs:248-256) skips them (D6). `addresses()` is then no longer an `ExactSizeIterator`. The 256-entry cap stays.
  - `Error::Duplicate` remains for CPU UID or APIC ID collisions, IOAPICs, ISA overrides, NMI sources and the LAPIC address override.
  - Captured fixtures (D8) from the reference VMware VM at 1 and 4 vCPUs. Next to each: the Workstation version, the .vmx values and vmware.log firmware line that D8 lists, and the Linux `apic=debug` IOAPIC lines.
- `kernel/src/acpi.rs:111-138`: per-entry handling (D6), which replaces the fail-closed comment at acpi.rs:112-116.
  - New marker `MIRROR_ACPI_TABLE_SKIPPED index=<n> address=<hex> reason=<error>`.
  - `MIRROR_ACPI_READY` (acpi.rs:141-150) gains the trailing fields `omitted_cpus= nmi_merged= nmi_conflicts= nmi_unmatched= skipped_tables=`. The scripts/run.ps1:503 regex only requires whitespace after `enabled=N`, so it still matches.
- `kernel/src/apic.rs:242-244` in `prepare` (D9): the ID register is still read once per IOAPIC, but a mismatch no longer returns `Err("ioapic_id_mismatch")`, and that skip reason goes away. A new pure function `ioapic_id_mismatch(firmware: u8, id_register: u32) -> Option<u8>` returns the register's bits 31:24 when they differ from the MADT ID. For each IOAPIC where it returns a value, `prepare` prints `MIRROR_APIC_IOAPIC_ID index=<n> firmware=<id> hardware=<id>` and continues with the MADT address and GSI base. The values are decimal, like `bsp=`, and `n` is the record's position in `topology.io_apics()`. The line therefore precedes `MIRROR_APIC_READY`, and it still appears if a later check skips the APIC. Nothing writes register 0. `IoApic`, `Controller` and the `MIRROR_APIC_READY` fields (apic.rs:156-160) are unchanged.
- `kernel/src/apic.rs:305-319` `lint_configuration`: apply wildcard records first, then UID-specific ones, so that the result does not depend on table order. The BSP (apic.rs:224) and the APs (apic.rs:573) both use it.
- `kernel/src/clock.rs`: `identify` (clock.rs:162-167) stops comparing against the table's block ID. `prepare` (clock.rs:132) logs `MIRROR_CLOCK_ID_MISMATCH firmware=<hex> hardware=<hex>` when the two differ. The hardware value must still have a nonzero REV_ID, a clear bit 14, a 64-bit counter and a period within range (clock.rs:163-178).
- `kernel/src/pci.rs`: `MAX_RETAINED` (pci.rs:33) becomes 256 and `pub(crate)`, and the doc comments at pci.rs:108, 567-568 and 813-816 are updated to match. The three `discover` functions, `drivers.rs:57-99` and `console.rs:347-395` need no change, because they already search or list the whole retained array. The fields of `MIRROR_PCI_READY` are unchanged.
- `kernel/src/drivers.rs:259`: the boot-smoke `test_inventory` (drivers.rs:250-262, used by drivers.rs:226 and console.rs:608, 679) builds a `pci::Inventory` literal with `devices: [None; 32]`. It becomes `[None; pci::MAX_RETAINED]`. Otherwise the boot-smoke build fails to compile, with an array length mismatch, once `MAX_RETAINED` is 256.
- `scripts/run.ps1`:
  - New `-CrowdedPci` switch that adds 32 root-port functions at 00:15.0-00:18.7, the slots where VMware puts its root ports. Each one is added like `-device pcie-root-port,bus=pcie.0,addr=0x15.0x0,multifunction=on,chassis=1,id=rp1,io-reserve=0`, with a unique `chassis` and `id` per port. `io-reserve=0` stops OVMF from exhausting the 64 KiB I/O space across 32 hotplug ports. It applies on top of any 0014 profile.
  - Near run.ps1:500-505, assert that no `MIRROR_ACPI_TABLE_SKIPPED` or `MIRROR_APIC_IOAPIC_ID` line appears and that every new `MIRROR_ACPI_READY` counter is 0.
- `kernel/src/ahci.rs` `issue` (D10): after CI clears, the immediate `TFD & TASK_BUSY` rejection becomes a bounded `wait_clear(port, TFD, TASK_BUSY, REQUEST_NS, AhciError::InvalidTransfer)`, and the TFD error check reads TFD after that wait. QEMU's AHCI model never shows the busy window, so a boot-smoke self-test drives the completion logic with a scripted register sequence (BSY set on the first reads after CI clears, then clear) if the code is factored to allow it; otherwise test 14 is the check.
- `scripts/common.ps1:68`: the `retained -gt 32` bound becomes 256.
- `scripts/test.ps1`: add test 11 to both build profiles, two boots in all. 0014 already computes the boot count (test.ps1:225).
- `readme.md` (or the `docs/` page that holds these sections under P5c):
  - :215: duplicate and surplus local NMI records and surplus CPU records no longer reject the topology (D3, D4), and the bounds list says 130 local NMI records.
  - :219: the HPET sentence drops the event-timer identity and descriptor-width checks (D5). The sentence "Invalid root resources or unreadable table identities still reject discovery" is replaced: only an invalid RSDP or root table rejects discovery, and null, repeated or unreadable root entries are skipped with `MIRROR_ACPI_TABLE_SKIPPED` (D6).
  - :221: the apic.rs sentence adds that an IOAPIC ID register that differs from its MADT record is reported with `MIRROR_APIC_IOAPIC_ID`, not rejected (D9).
  - :299 and :333: 32 retained functions become 256 (D7).
- `AGENTS.md` (0012, ledger P9), in the same commit as the D3-D6 and D9 changes: the "Fail closed" coding convention names firmware tables among the inputs where anything unknown or malformed is rejected. Reword it so that firmware tables are still validated before use, but duplicate or surplus MADT records and null, repeated, unreadable or unused root-table entries are tolerated: dropped or skipped, counted, and reported in markers (D3, D4, D6). HPET descriptor fields that Mirror does not use are ignored (D5). An IOAPIC ID register that disagrees with its MADT record is reported, not rejected (D9). Also update any other line this spec makes stale, such as a list of `run.ps1` device switches (`-CrowdedPci`).

## Acceptance tests
Host tests (`cargo test -p mirror-acpi`, which scripts/test.ps1:74 already runs):
1. Dual wildcard NMI: `[local_nmi(0xff, 1, 0), x2nmi(u32::MAX, 1, 5)]` parses, with `local_nmis().len() == 1` and `merged_nmis == 1`. The four tests.rs:544-547 cases each gain a CPU record with UID 4. They then parse with 1, 2, 2 and 1 local NMIs respectively, and `merged_nmis` of 1, 0, 0 and 1. Other tests with UID-specific NMI records and no matching CPU record (tests.rs:511, 687-696) gain CPU records or new expectations, because D4 drops unmatched records.
2. NMI conflict: `[local_nmi(0xff, 1, 0xd), x2nmi(u32::MAX, 1, 5)]` parses, keeps the first record (level-triggered) and reports `conflicting_nmis == 1`.
3. VMware-style per-slot records:
   - 128 type-0 records (4 enabled, 124 with flags 0) followed by 128 type-4 records (UIDs 0-127, LINT1, flags 5) give 4 CPUs, 4 local NMIs and `unmatched_nmis == 124`. Today the same input returns `Error::Capacity`.
   - With the 124 slots marked online-capable (flags 2) instead, the result is 64 CPUs including all 4 enabled ones, `omitted_cpus == 64`, 64 local NMIs and `unmatched_nmis == 64`. This case is not VMware's layout: VMware's revision-3 MADT never sets flags 2.
   - Interleaved, in the record order of VMware's MADT builder (added 2026-10-10): `[cpu(i, 2 * i, if i < 4 { 1 } else { 0 }), local_nmi(i, 1, 5)]` for i in 0..128, then `io_apic(0x80, 0xFEC00000, 0)`, `iso(0, 2, 5)`, `iso(9, 9, 0xf)` and `iso(10, 10, 0xf)`, in a MADT with revision 3 and flags 1. It gives 4 CPUs, 4 local NMIs, `unmatched_nmis == 124`, 3 overrides and one IOAPIC with `id == 0x80`, the MADT side of test 8's D9 case. The APIC IDs of 2 * i follow a VMware BIOS guest and are illustrative.
4. Truncation:
   - 65 enabled CPU records give 64 CPUs and `omitted_cpus == 1`.
   - 60 online-capable records followed by 10 enabled ones give all 10 enabled CPUs plus the first 54 online-capable ones, in table order, with `omitted_cpus == 6`.
   - IOAPIC and NMI source overflow still return `Error::Capacity` (tests.rs:660-707 adjusted).
5. HPET: GAS bit widths 32 and 64, access sizes 1-4, a nonzero bit offset, and block IDs with REV_ID 0 or bit 14 set all parse to the same address. Nonzero space IDs still return `Error::Address` (tests.rs:138-163 adjusted).
6. Root: a null entry is skipped, and a repeated address yields one address. 257 entries still return `Error::Capacity` (tests.rs:379-400 adjusted).
7. Fixtures (D8): each captured VMware MADT and HPET table parses. The test asserts the CPU, IOAPIC and local NMI counts, the IOAPIC's MADT ID and the diagnostics observed in test 14.

Boot-smoke self-tests:
8. `apic::self_test` (apic.rs:759-991):
   - (apic.rs:886-913) `lint_configuration` returns the same values for [specific, wildcard] and [wildcard, specific] on one LINT.
   - D9, with no MMIO: `ioapic_id_mismatch(0x80, 0)` returns `Some(0)`. That is VMware's case with 128 slots, MADT ID 0x80 and a register reading 0, and it is accepted and reported. `ioapic_id_mismatch(0, 0)` (QEMU) and `ioapic_id_mismatch(0x80, 0x8000_0000)` return `None`, and register bits 23:0 are ignored: `ioapic_id_mismatch(5, 0x05ff_ffff)` returns `None`.
9. `clock::policy_self_test` (clock.rs:340-361): the case at clock.rs:344 is accepted and reported as a mismatch. A hardware value with REV_ID 0 or bit 14 set is still rejected.
10. `pci::self_test`:
    - A synthetic 40-function scan whose last function is AHCI-class retains all 40 and finds the AHCI function with the `is_ahci` predicate.
    - The crowded scan (pci.rs:964-973) retains 256 functions with `omitted == 7936`.

QEMU cases (scripts/test.ps1, debug and release):
11. `run.ps1 -Smoke -CrowdedPci`, on 0014's default `V1` profile:
    - `MIRROR_PCI_READY` reports `functions=39 bridges=32` and `omitted=0`. That is `V1`'s 7 functions plus the 32 root ports.
    - `V1`'s e1000 sits at a bus-0 slot below 00:15, so the `ahci-sata` record (00:1f.2) is the 38th `MIRROR_DRIVER_DEVICE` record.
    - `MIRROR_AHCI_READY` and `MIRROR_AHCI_READ_OK` appear, and 0014's catalog check finds the one `8086:100f` record.

## Open questions
1. Assumptions about VMware firmware, to be confirmed by tests 14 and 16 and the D8 capture. (Amended 2026-10-10: static analysis of Workstation Pro 26.0.1 build 25688693 settled most of them. It read the AcpiPlatformDxe and AcpiSupportDxe modules of EFI20-64.ROM and EFI64.ROM, whose MADT and HPET builders agree, plus vmware-vmx.exe and vmwarebase.dll. Each item says what it showed; a boot still confirms each.)
   - MADT CPU records. For each present CPU slot the firmware emits a type-0 record followed by a UID-specific type-4 record (LINT1, flags 5), or type 9 plus type 10 when the APIC ID exceeds 0xFE. Present-but-disabled slots have flags 0, and flags 2 never appears. The slot count comes from the VMX: the larger of `numvcpus` and the configured maximum. VMware guests have shown 128 slots, and a 4-vCPU BIOS guest showed 4. With more than 64 slots, today's 64-entry NMI limit (lib.rs:23) rejects the MADT; with 64 or fewer it already parses.
   - Other MADT records. After the CPU records come one IOAPIC, ISO 0->2 (flags 5) and zero or more level ISOs (source = GSI = n, flags 0xF), one for each PCI IRQ the firmware allocated as level-triggered. There are no wildcard NMI, type-3 or type-5 records. Assumed: every VMware ISO has a source below 16, and no source or GSI repeats (lib.rs:405-407, 416-422).
   - PCI layout. Workstation 26H1's create paths (vmwarebase.dll, used by the GUI and by vmcli) add pciBridge0 plus pciBridge4-7, each a `pcieRootPort` with 8 functions: 32 root ports (verified). An ESXi BIOS guest's log and Broadcom KB 311606 place the root ports at 00:15.0-00:18.7, count 40 bus-0 functions, 34 of them bridges, and put the SATA controller and the NIC on bus 02 behind pciBridge0, past the current cap. Workstation assigns slots at first power-on, so test 14 confirms the placement. The VM does not come close to 256 functions.
   - PCI IDs (verified from the option ROM headers and vmware-vmx's config-space template): AHCI 15ad:07e0, class 01:06:01, with PM, 64-bit MSI and SATA capabilities and no BAR4; e1000 8086:100f (82545EM); SVGA II 15ad:0405.
   - VMware:
     - sets PCAT_COMPAT (verified; MADT revision 3, OEM VMWARE/EFIAPIC) and has one IOAPIC (verified: 0xFEC00000, GSI base 0, 24 inputs). Its MADT ID is the first unused CPU slot, at least 1, while its ID register resets to 0 (D9);
     - emits no type-3 NMI source records (verified; apic.rs:196-198 refuses them);
     - hands off in xAPIC mode. Not settled statically: the handoff depends on the `apic.x2apic.*` keys and platform flags. `other-64` brings no x2APIC default, unlike `windows11-64`;
     - places the RSDP, XSDT, MADT and HPET in memory that Limine reports as ACPI reclaimable, ACPI NVS or bootloader reclaimable (acpi.rs:270-273 refuses everything else). Verified on the firmware side: the RSDP, RSDT, XSDT and every table except FACS and OEMD share one EfiACPIReclaimMemory buffer below 4 GiB, and FACS and OEMD are in ACPI NVS. That Limine reports this type as ACPI reclaimable is inferred.
   - VMware's HPET has a 64-bit counter and a period of 1-100 ns. Verified: GCAP_ID 0x0429B17F_8086AF01, which means REV_ID 1, bit 14 clear, 16 timers, a 64-bit counter and a period of 69,841,279 fs (14.31818 MHz). The table has address 0xFED00000, minimum tick 14318, page protection 1 and an all-zero GAS. Its block ID comes from a VMX value and is expected to be 0x8086af01, as an ESXi guest showed. The firmware publishes the table only when the VM has an HPET: new VMs at virtual hardware 8 and later get `hpet0.present = "TRUE"`, but vmware-vmx treats a missing key as FALSE.
   - Firmware leaves each AHCI controller with memory decode on, MSI off, a 32-bit non-prefetchable ABAR and power state D0 (pci.rs:509-511, 516, 537-541). Not settled statically; test 14 and the D8 capture's `lspci -nn -vv` show it.
