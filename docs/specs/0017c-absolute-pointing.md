(Confirmed 2026-10-09.)

Implementation notes (2026-10-12):
- A drain reads STATUS once, then up to 64 DATA packets; a longer queue sets the vmmouse pending flag (D13).
- SKIPPED reasons: GETVERSION fails gives `no_backdoor`, with no DISABLE, since nothing answered; a STATUS after READ_ID with a zero low half or a 0xFFFF high half gives `no_device`; a DATA reply other than the version ID gives `version`; a final STATUS error gives `status`.
- `State::accept` returns whether a doorbell rang, and `accept_byte` then runs the drain, so `accept` stays testable without port I/O. `SurfaceRegion::origin` and `surface::Session::placement` give the input session the framebuffer size and the desktop rectangle.
- The shell's pointer handling moved into one `Shell::pointer`, which relative motion and kind-4 positions share.
- `capture.ps1` asserts acceptance 4's exact rejection text, "Input handler not found for event type abs". `-Hygiene -RelativePointer` also works, beyond the spec.
- VMware quirk, not a Mirror defect: in all three check boots the first pointer event after power-on had no visible effect, an identical second event applied, and every later event applied at once. A throwaway debug build (2026-10-12) counted AUX bytes, doorbells and drained packets: the first VNC move delivered no PS/2 byte and queued nothing, and the second delivered one doorbell (`28 01 ff`) and a one-packet queue. So VMware drops the first pointer event before the guest. Harnesses that drive Mirror over VNC (0018) send a priming move after boot.

The manual VMware check also needs 0013 and 0015a's disk image. 0018's Mirror input rows follow this spec (0018-D12).

## Goal
In VMware the pointer is not grabbed: Mirror's cursor follows the host pointer into and out of the VM window, placed by absolute coordinates from the VMware vmmouse protocol, which rides on the existing PS/2 mouse. QEMU's `vmport` vmmouse runs the protocol in the automated tests, and 0018 places Mirror's pointer with absolute VNC coordinates and no homing step (0018-D12). When the protocol is absent or fails, the relative PS/2 mouse of 0017a and 0017b carries on. Keyboard input and 0017a's loss domains are unchanged. This fills a modern-OS baseline gap (G12).

## Non-goals
- USB HID pointing, relative or tablet: after v1, with physical hardware (S1d).
- Wheel and extra buttons (0084). The vmmouse wheel word is read and ignored.
- Display size and live resize (0069, 0027a). Until 0027a lifts the 1280x800 desktop cap (`kernel/src/surface.rs:37-39`), host positions in the border around the centered desktop clamp to its edge.
- The rest of the VMware backdoor (guest RPC, clipboard, shared folders: 0087). This spec issues only the commands in D11-D13 and D16 (GETVERSION 10, ABSPOINTER DATA 39, STATUS 40, COMMAND 41, RESTRICT 86).
- Seats, provenance, the agent cursor (0047, 0027a's envelope), pointer acceleration, multiple monitors.

Rationale: QEMU raises a fake PS/2 packet with dx=+1 per vmmouse event (`ps2_mouse_fake_event`), and Linux uses the PS/2 bytes only as a trigger (`vmmouse.c:197-210`). | 0017-D14 | Decode: status bits `0x20`, `0x10`, `0x08` are LEFT, RIGHT, MIDDLE (`mouse.rs:19-21`). Bit 16 marks a relative packet: dx = x, dy = -y, saturated to i16. Otherwise x and y are absolute, 0..0xFFFF (a larger DATA value saturates to 0xFFFF), and the ring keeps device units. Consumers convert at use with `px = (x * (W - 1) + 0x7FFF) / 0xFFFF`, so 0 and 0xFFFF are the first and last framebuffer pixel and a later mode change (0069) needs no driver change. `input::Session::encode` subtracts the desktop rectangle's centered origin (`surface.rs:41-56`) and clamps, so kind 4 carries surface-local pixels (D17); the kernel console's `Pointer::place` uses framebuffer pixels directly. Rationale: exact endpoints, and QMP's range round-trips exactly (test 1). Rejected alternative: the kernel turns positions into relative deltas, which drift from the desktop's clamped position. | confirmed (2026-10-09) |
| 0017-D15 | Absolute events share the 64-entry mouse ring and the shared sequence, so they stay ordered against keys (0017-D3). ## Interfaces
**Backdoor** (`kernel/src/vmmouse.rs`, new)
- `unsafe fn backdoor(command: u32, argument: u32) -> [u32; 4]`: EAX = `0x564D5868`, EBX = argument, ECX = command, DX = `0x5658`, `in eax, dx`; returns EAX to EDX, with ESI and EDI clobbered (linux `arch/x86/include/asm/vmware.h:9-47`). LLVM reserves RBX for inline asm, so the call swaps EBX through a scratch register. Access is a 32-bit `in eax, dx` only: the protocol returns its result in EAX, and QEMU's vmport implements only 4-byte access (`.impl`), widening narrower accesses rather than rejecting them. BSP with IF clear, as `mouse.rs:269-271`.
- Device markers, no user content: `MIRROR_VMMOUSE_READY mode=absolute`; `MIRROR_VMMOUSE_SKIPPED reason=no_mouse|no_hypervisor|no_backdoor|no_device|version|status`; `MIRROR_VMMOUSE_FALLBACK reason=status|queue_length`, once. At runtime the IRQ side records the reason and the next `ps2::next_event` prints it, since `accept_byte` never prints (`mouse.rs:291-292`). READY, SKIPPED and the runtime FALLBACK print in every flavor. FALLBACK can follow pointer input, which ledger S7b (reworded 2026-10-09) allows for content-free device markers.

**Kernel paths**
- `mouse.rs`: `State` gains a doorbell mode, set by `vmmouse::init`, in which `State::accept` (`mouse.rs:189-231`) drains. The ring holds `PositionEvent { x: u16, y: u16, buttons: u8 }` beside `MouseEvent`; `ps2::InputEvent` (`ps2.rs:293-303`) gains `Position`.
- Kernel console (`main.rs:658-674`): new `Pointer::place(x, y, buttons)` maps to framebuffer pixels and shares click arming with `apply` (`pointer.rs:42-62`). `MIRROR_POINTER_UPDATED` (`main.rs:713-722`) is unchanged.
- `input::Session::new` (`input.rs:20-39`) takes the framebuffer width and height and the desktop rectangle in framebuffer pixels, from `surface::Session::desktop` in `run_desktop` and `run_shell` (`userspace.rs:1224-1225`, `:2028-2029`); `encode` (`input.rs:60-116`) emits kind 4.
- Desktop: `decode_event` (`userspace/desktop/src/main.rs:97-144`) accepts kind 4 and rejects nonzero words 3-5 and out-of-surface positions. The shell (`shell.rs:511-531`) and Scratchpad (`ui.rs:265-282`) set the position directly and keep click arming. App pointer records are unchanged.
- Smoke fault (boot-smoke only, S7a): `mirror.test=vmmouse-error` (`SmokeMode::VmmouseError`). After READY, init reads DATA from the empty queue, which QEMU answers by disabling the device, then runs one drain as a doorbell would.

**Scripts** (on 0014's profiles)
- `run.ps1`: `-NoVmport` adds `vmport=off` to the machine (`run.ps1:352-355`); `-Fault VmmouseError`; the PS/2 marker checks (`run.ps1:765-788`) gain the vmmouse markers. `-NoKeyboard` already sets `vmport=off`.
- `capture.ps1`: absolute helpers beside `capture.ps1:248-270` send `abs` x and y in one `input-send-event`, with `v = round(p * 0x7FFF / (W - 1))` for framebuffer pixel p of width W; desktop targets add the centered origin from `MIRROR_FRAMEBUFFER_READY` and the desktop or shell READY marker. Buttons stay separate events. `capture-shell.ps1:14-43` uses them. 0010's `-Hygiene` probe (a default build with `vmport` on) uses them too: in its acceptance step 3.2, one `abs` move to the Notes launcher replaces the (-2560,-1600) clamp and the (64,776) move, and step 3.3's (100,-100) move becomes an `abs` move to the point 100 px right of and 100 px above the previous one. Default builds print no SHELL or DESKTOP READY marker (0010 step 3.5), so `-Hygiene` takes the desktop origin from `MIRROR_FRAMEBUFFER_READY` and the centered 1280x800 cap (`kernel/src/surface.rs:38`). 0019's `mirror.perf=1` rerun of the probe inherits this. `-RelativePointer` boots with `vmport=off` and keeps today's helpers.
- `AGENTS.md` (P9): the "When to test" line for desktop, console, input or display code adds `capture.ps1 -NoBuild -RelativePointer`, the suite line counts the relative capture, and `-NoVmport` joins any list of `run.ps1` device switches.
- **Files touched:** `kernel/src/{vmmouse (new),mouse,ps2,pointer,input,main,userspace,boot}.rs`, `userspace/desktop/src/{main,shell,ui}.rs`, `scripts/{run,test,capture,capture-shell}.ps1`, `readme.md:352, 358, 362, 531`, `AGENTS.md` (P9).

**Protocol facts** (references only, P6; nothing copied). Linux `drivers/input/mouse/vmmouse.c:27-58` (constants), `:126-158` (drain loop, relative bit). QEMU at v10.1.0, the tag Mirror's code cites (`ps2.rs:9-11`; the local binary is 11.1.0): `hw/i386/vmmouse.c` scales QMP's 0..0x7FFF to 0..0xFFFF, sets bit 16 only in relative mode, disables the device on an over-long DATA read, and starts disabled after reset; `hw/i386/vmport.c` serves port `0x5658`, implementing only 4-byte access (`.impl`, no `.valid` limits), answers unregistered commands with `0xFFFFFFFF`, and has no CPL check; `ui/input.c` `qmp_input_send_event` rejects an event type with no handler, so `abs` fails until the guest requests absolute mode; `target/i386/cpu.c` `x86_cpu_load_model` sets the hypervisor bit for named models (qemu64), and `-cpu max` (`-ExtendedCpu`, `run.ps1:352`) gets it through max_features, because `TCG_EXT_FEATURES` includes `CPUID_EXT_HYPERVISOR`. `vmport=auto` is on unless `accel=xen` or `i8042=off` (`.tools/qemu/share/doc/system/invocation.html`).

1. `vmmouse::self_test` (MIRROR_VMMOUSE_TESTS_OK), pure functions with a fake backdoor, no port I/O:
   - Status `0xFFFF0000` and a queue length of 6 are errors. Buttons map as D14; bit 16 gives dx=x, dy=-y with i16 saturation.

## Open questions
1. Resolved 2026-10-12 by D19 (Cameron adopted the proposal below after check 7). The original question: Security. VMware services backdoor port I/O from CPL3 even when IOPL and the TSS I/O bitmap deny it; KVM imitates this only behind `enable_vmware_backdoor` (linux `arch/x86/kvm/emulate.c:2540-2546`). Any Mirror user process could therefore reach the host channel outside the capability model (the whole backdoor now: GETVERSION and the other information commands, and the guest RPC channel on `0x5658` command 30 and the high-bandwidth port `0x5659`, through which a process can speak the RPC and clipboard protocol itself whether or not 0087 exists; not the absolute-pointer commands, which D12's RESTRICT limits to CPL0, though that the caller's CPL reaches vmware-vmx in Host VBS (ULM) mode is inferred); IOPL 0 and the bitmap-free TSS (`kernel/src/interrupts.rs:39-41, 75-76`) do not stop it. QEMU TCG checks I/O permission before vmport runs, so the automated tests cannot show it. The VMX option `monitor_control.restrict_backdoor = "TRUE"` limits the backdoor to CPL0, which suits this kernel driver but would force a userspace 0087 service through a kernel broker. Proposed: Mirror's VMs set it, which keeps backdoor access, including the 0087 guest RPC channel, in the kernel. It applies only to Mirror's VMs (0015a's reference VM in `docs/vm-settings.md`, and 0018's Mirror VM); 0018-D3 would then list it as an accepted exception, because VMware Tools in the Ubuntu and Windows baselines needs user-mode backdoor access. Static evidence (2026-10-10): the key is present in 26.0.1 build 25688693; in the traditional-mode monitor it gates every access to port `0x5658`/`0x5659` with the magic when CPL > IOPL (`InOut_EmulateWithHint`, `Priv_HyperCall`). Check 7 records the vmware.log `Monitor Mode:` line, because the Host VBS (user-level monitor) path was not analyzed, and the development host runs that mode (`Monitor Mode: ULM`, scratch power-on 2026-10-10).
