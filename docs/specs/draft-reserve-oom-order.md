# Reserve and OOM order (proposed follow-up to 0054a; unnumbered pending RD24)

Status: superseded (2026-10-12), because 0054a carried the reserve and OOM order to `main` @4c05b02 (C8 settled 2026-10-12, S18 stands). Its 0054-D4 to D6 rows remain the reference for that part of 0054a.
Depends on: 0054a (the refcount allocator and the class model, 0054-D1/D2), 0030a (the process table, wait-queue unlinking, zombie/reap, 0030-D1/D2/D5), 0050 (its stack pool is trimmed before and during victim choice, 0050-D2) and 0059 (0059-D3's charged-frames counter ranks victims).
Ledger: S18 (the reserve and the OOM order; this split proposes amending it and RD6 until Cameron decides C8), S6 as amended 2026-10-12 (no syscall). Related: S4, G7, I6, RD6.

Line references are at origin/main 8e43e55.

## Goal
The kernel gains S18's memory policy (decisions.md:140): a reserve that only the kernel and the protected classes may draw, and an out-of-memory victim order — background work, then agent tasks, then normal apps, never the compositor, shell or system services — that runs whenever a frame allocation fails for lack of frames. A failing request kills a lower-class victim and retries, instead of today's "the faulting process kills itself" (userspace.rs:1034-1039) as anything but the last resort. The class limits lift with it (0054a keeps them at today's values until this spec lands): normal, agent and background to 1 GiB reserved / 512 MiB committed, protected bounded by the arena and free memory (open question 1).

## Non-goals
- Pressure notifications (0054b, Phase 11); the engine/indexer's shrink behavior.
- Refcounts and the class table's mechanism (0054a). This spec lifts the values; it does not change the plumbing.
- Userspace on APs (0051): allocation stays BSP-only with IF=0. 0051 inherits three obligations: the reserve check must be atomic with the allocation; count updates run under the allocator's lock; and a victim running on another CPU must be stopped and its TLB entries shot down before teardown.
- Any new syscall (S6, amended).

## Decisions
| ID | Decision | Status |
| --- | --- | --- |
| 0054-D4 | The reserve is a free-frame floor — the smaller of 16 MiB and one sixteenth of usable frames (open question 2) — fixed once at one point identical in every flavor before the first session, and printed once as `MIRROR_MEM_RESERVE frames=<n>` (content-free). Every runtime frame consumer reserves its operation's worst-case frame count against the floor before it starts (the 0059-D1 preflight pattern: one check per operation), so no partial operation straddles the floor. The check serves the kernel's own calls (which may draw the floor) and each class's: a non-protected class's operation refuses to cross the floor. Sites: materialize's page tables and data pages (vm.rs:398-478), create_process's image and stack, 0050's stack builds, and pixels (windows.rs:37-64). Boot-time DMA is the kernel's call and never selects a victim (a contiguous DMA32 failure can be fragmentation, memory.rs:153-190, which no kill fixes). Heap growth uses the kernel's call and keeps 0059-D1's back-off, never selecting a victim. A launch's create, stack builds and pixels are governed by the *child's* class (0054-D2 sets it at create), so a launch never draws the reserve or kills a running app of its own class; a failed launch picks candidates for the child's class (open question 13). Rationale: one preflight per operation keeps the floor's invariant without threading a class through paging.rs and windows.rs. Rejected alternative: a class-scoped allocator view through paging.rs, windows.rs and 0050's builder. | proposed |
| 0054-D5 | Victim selection runs whenever a frame allocation fails for lack of frames — at the floor or at zero, never only at global exhaustion. Only a failed frame allocation triggers it: frame exhaustion gets its own kernel-internal error (a `VmError::NoFrames` that becomes -12 only at the syscall boundary), so a process at its own commit limit (vm.rs:411-413's quota failure, unchanged) never triggers it, and launch keeps OutOfFrames distinct instead of mapping every error to -12 (userspace.rs:1440). Candidates: for a non-protected requester, only strictly lower kill classes (S18's order: background below agent below normal; the test class ranks with normal and may not draw the reserve — open question 11); for a protected or kernel requester, every non-protected class. Within a class: the largest footprint — owned pages plus the 0059-D3 charge (page tables plus the kernel-frames counter), each counted once — then the newest PID. Before choosing, trim 0050's stack pool; trim again after each kill, before the retry (both new trim points are open question 12, amending confirmed 0050-D2). A kill finishes the victim at once in the completion context — Outcome::OutOfMemory (open question 6), threads unlinked (0030-D2), handles closed, its address space destroyed immediately (the victim is never running: the scheduler is BSP-only with IF=0 until 0051) — and its zombie keeps only the Outcome for validation, so the reap skips the destroy for an OOM zombie (amending confirmed 0030-D5, also open question 12). The failed allocation retries once per kill, bounded, stopping at success or when no candidate remains. record_fault's self-kill (userspace.rs:1034-1039) is the last resort: with no candidate left, a protected process's failed fault still kills it, the shell session then ends, its children end SessionEnded and default and trace kernels start the console (0030-D5; smoke kernels go on to the capacity self-test). Rejected alternative: kill the requester always (a background hog then outlives a normal app, against S18). | proposed |
| 0054-D6 | Markers and scripts for this half. `MIRROR_MEM_RESERVE frames=<n>` prints once per boot in every flavor and joins test.ps1's Default and Trace `$required` lists (test.ps1:36, :40), checked exactly once with its full field list in run.ps1 and capture.ps1, the script recomputing frames= from MIRROR_FRAME_POOL's total= and the floor's sizing rule. `MIRROR_OOM_KILL class=<class> pid=<n>` prints per victim kill (flavor gating per open question 5; recommended: every flavor, a content-free lifecycle marker under S7b, staying off the `$forbidden` image lists with run.ps1 rejecting it by scenario). Outcome::OutOfMemory maps to `reason=oom` in MIRROR_APP_RECLAIMED, and the shell reads it as FAULTED with detail 0 (the window-protocol state set, crates/window-protocol/src/lib.rs:29-31, is unchanged — S6's amendment allows no Phase 1 ABI change), counted in windows.faults (userspace.rs:1514-1516). The mapping lands only where outcomes survive 0030a: the shell's reclaim and the zombie validation. Rationale: the OOM kill is a lifecycle event the owner must be able to see (S17's log follows in Phase 3), and the reserve is a boot-time contract the scripts can recompute. | proposed |

## Interfaces
- `kernel/src/memory.rs`: the floor and the worst-case preflight helper (one check per operation; no `allocate_for` is added — the preflight is the mechanism, and the kernel's `allocate` runs under it).
- `kernel/src/vm.rs`: `VmError::NoFrames` (becomes -12 only at the syscall boundary); the quota failure keeps its ENOMEM; the lifted limits apply at :190-193 and :411-413.
- `kernel/src/sched.rs` (0030a): victim selection, the kill/reap split and the bounded retry run in the scheduler's completion context; a boot-smoke self-test drives the selection function over synthetic entries (background, agent, normal, test and protected; footprints; PIDs) for order, tie-breaks and the protected exclusion.
- `kernel/src/userspace.rs`: the frame-failure sites (:1034-1039, :1058-1062, :1440 with the distinct error) route through selection; :1012 (reserve/release/protect) never does.
- `kernel/src/windows.rs`: a pixel-allocation failure routes like the create failure (it is a frame failure on the launch path, on the child's class).
- `kernel/src/boot.rs` and `main.rs`: the `oom-order` token and SmokeMode beside the existing modes; the reserve is fixed and printed before the first session; the kernel-wide frame budget (a memory.rs value armed only in this scenario) is set there.
- 0050's kernel_va.rs: the trim is callable from the completion context, before a victim choice and after each kill (open question 12).
- `userspace/init`: the OomOrder scenario's processes; init's argument encoding gains a mode for the victim's background class (init main.rs:1107-1109's bound is unchanged; the encoding, not a probe number); validate_process excludes the scenario (userspace.rs:2214).
- Scripts: run.ps1 gains `-Fault OomOrder` (ValidateSet, `$testMode`), asserts OOM_KILL only there; test.ps1 adds the case in both profiles and the `-MemoryMiB 1024` commit case (the Phase 1 exit, roadmap-replan.md:135); common.ps1 gains the MEM_RESERVE recompute; capture.ps1's absent list follows open question 5. The relaunch pair's replacement changes these counts in the same commit: MIRROR_USERSPACE_OK (run.ps1:598-600), sync (:640-645), TLS (:652-657), threads (:660-663), FPU (:673-676), the VM line (:679), 0059's per-drain CHARGE_OK (0059-D4), 0050's KSTACK_OK and 0030a's PREEMPT_OK.
- readme.md: the pool paragraph (:317) and the fault-behavior lines (:327, :547), in the same commit.

## Acceptance tests
1. The existing battery passes unchanged apart from the relaunch pair's replacement (its marker counts are updated per Interfaces).
2. `-Fault OomOrder` (`mirror.test=oom-order`): the scenario replaces the relaunch pair with a normal requester and a background victim (two processes, the pair's end rule, 0030-D1). The armed kernel-wide budget shrinks only this scenario and lifts before the session drains. Assert: the background victim dies with Outcome::OutOfMemory, `MIRROR_OOM_KILL class=background` prints exactly here, the requester's retry succeeds after the kill, the reserve holds, and the shell session seeds and runs normally afterwards. The selection self-test (Interfaces) proves the order, tie-breaks and the protected exclusion that the two-process session cannot.
3. Reserve: a boot-smoke self-test right after the floor is fixed drives the preflight to it: a normal class's operation is refused while the kernel's own `allocate` still succeeds, with frame counts restored.
4. Limits, lifted with the reserve: a `mirror.test=` scenario gives init's process the normal class at seeding; it reserves to its bound and one page past (reservations take no frames), commits 256 MiB in the `-MemoryMiB 1024` boot (frame counts restored, 0050-D2's rule), and fails at its commit bound where frames allow. One protected process reserves past 4 GiB (no frames) and SYS_VM_STATS reports it — I6's Phase 1 mechanism, proven (open question 4 of 0054a).
5. `reason=oom` is exercised where an outcome reaches the shell; if the scenario's victim never reaches it, that is stated instead.
6. Before merge (P8): the full `scripts/test.ps1` in debug and release, plus `-AgentDemo` while the agent-demo feature exists (RS6). The marker changes land in the same commit.

## Open questions (for Cameron, with the reviewer's recommendations)
1. The class limit table, taking effect with this spec (C3). Recommended: normal, agent and background at 1 GiB reserved / 512 MiB committed; protected bounded by the arena and free memory; the test class keeps 256/32 MiB; 0022's grants raise limits later. Alternative: scale normal's limits with usable RAM.
2. The reserve's size and who may draw it (C2). Recommended: the smaller of 16 MiB and one sixteenth of usable frames, as a free floor; the kernel and protected classes may draw it (0054-D4). Alternative: a fixed size only.
3. Victim selection at the floor for a normal app or agent (C1). Recommended: yes — background first, then agent (0054-D5). Alternative: fail the requester at the floor, as today.
4. Refcount width (C4): settled in 0054a's open question 2 (u16).
5. Does `MIRROR_OOM_KILL` print in every flavor (C5)? Recommended: yes (S7b); it stays off the `$forbidden` image lists and run.ps1 rejects it by scenario. Alternative: boot-smoke only.
6. `Outcome::OutOfMemory` as a new variant with `reason=oom`, shown to the shell as FAULTED with detail 0 (C6)? Recommended: yes. Alternative: reuse Terminated, with only the marker to tell them apart.
7. What counts toward victim choice in Phase 1 (C7). Recommended: owned pages plus the 0059-D3 charge, each counted once. Alternative: charged, image and stack frames also count toward limits.
8. The split (C8): proposed — 0054a keeps every class at today's values and this spec lifts them together with the reserve. It amends RD6 and S18; until Cameron decides, S18 stands and 0054a carries the reserve and the OOM order. After a yes, claude edits S18's text, RD6's row (roadmap-replan.md:521), the Phases note (decisions.md:187), roadmap-replan.md:124, :420 and :486, README.md's map line for 0054a, and 0059:5/:15. Alternative: one 0054a (about 3,300 words), as RD6 and S18 say.
9. The follow-up's number (RD24). Recommended: 0054c, in Phase 1 right after 0054a and before 0051, keeping 0054-D4 to D6. Alternative: 0054b, moving pressure notifications to 0054c, which amends RD6 and roadmap-replan.md:383.
10. The OOM case's background-class process is a boot-smoke-only class given at seeding (C10, recommended), not init's Probe — so the battery's test class keeps today's constants and today's kill semantics. Alternative: a background CpuPolicy ahead of 0052.
11. The test class's rank and reserve access (C16). Recommended: ranked with normal for victim choice, and no reserve access. Alternative: ranked below background (killed first).
12. The two amendments to confirmed decisions (C13): 0030-D5's reap skips the destroy for an OOM zombie, and 0050-D2 gains two trim points (before choosing and after each kill). Recommended: yes, with this spec. Alternative: destroy every finished process's space at finish (a wider 0030-D5 change).
13. Whose class governs a launch's create, stacks, pixels and victim choice (C15). Recommended: the child's, so a launch never draws the reserve or kills a running app of its own class (0054-D4/D5). Alternative: the shell's (protected).
14. Does 0018-D6's idle memory keep counting the reserve as available (C12)? Recommended: yes, unchanged; reports also show MIRROR_MEM_RESERVE. Alternative: subtract the reserve, as Linux's MemAvailable does, and re-confirm 0018-D6.
