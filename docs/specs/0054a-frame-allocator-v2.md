# 0054a: Frame allocator v2 — refcounts, per-process limits, the reserve and the OOM order

Status: draft (revised after claude's review of 8762d0e)
Depends on: 0030a (the process table, its per-entry policy class, its wait-queue unlinking and its zombie/reap, 0030-D1/D2/D5), 0050 (its stack pool is trimmed before victim choice, and its shared frame-check rule), and kernel heap v2 (its per-process kernel-frames counter, heapv2-D3). Ordered fifth in Phase 1 (roadmap-replan.md:124), before 0051. The reserve and OOM decisions wait on RD6 (proposed, due before Phase 1).
Ledger: S18 (the reserve and the OOM order), S6 as amended 2026-10-11 (a vm-protocol limit change; no syscall). Related: I6 (multi-GB per-process memory), S4 (the background class), RD6.

Line references are at HEAD 58461e0 (the cited files are unchanged from 970e48c). origin/main has since moved; the spec owner remaps.

## Goal
The frame allocator gains per-frame reference counts, so sharing (0025's shared memory, the ELF loader v2's shared text) has a safe foundation. Per-process memory limits stop being the compile-time constants every process shares (vm-protocol's 32 MiB / 256 MiB, crates/vm-protocol/src/lib.rs:17-18) and become per-process state set at spawn from the process's class — with normal lifted past 32 MiB, since the 32 MiB commit is one of the foundations this phase lifts (roadmap-replan.md:58) and the Phase 1 exits commit 256 MiB in one process. And the kernel gains S18's memory policy: a reserve only the kernel and the protected classes may draw, and an out-of-memory victim order — background work, then agent tasks, then normal apps, never the compositor, shell or system services (decisions.md:140) — that runs whenever a frame allocation fails, replacing today's "the faulting process kills itself" (userspace.rs:1034-1039) as anything but the last resort.

## Non-goals
- Pressure notifications and cache-shrink requests (0054b, Phase 11; S18's engine/indexer behavior waits for it).
- Userspace on APs and the allocator's locking (0051): allocation stays BSP-only with IF=0 (memory.rs:210-215, :313-314). 0051 inherits three obligations: the reserve check must be atomic with the allocation; count updates must run under the allocator's lock; and a victim running on another CPU must be stopped and its TLB entries shot down before teardown.
- Grant-carried per-agent limits (0022, Phase 2; S18's "grants can carry per-agent memory limits"); limits here come from the class only.
- Heap growth policy (heap v2). Charged kernel frames (heapv2-D3's page tables and surfaces, 0050's stacks): whether they count toward a limit or toward victim choice in Phase 1 is Cameron's (open question 7); the counters exist either way.
- A free list or faster scans: the 2-bit bitmap and its scans stay (memory.rs:55-86).
- The vm-protocol ARENA bounds and MAX_REGIONS (64, after 0030a).

## Decisions
| ID | Decision | Status |
| --- | --- | --- |
| 0054-D1 | Per-frame refcounts in a companion u16 array (2 bytes per frame, reserved once at boot as METADATA beside the 2-bit state bitmap through the mechanism `enable_recycling` already uses, memory.rs:249-263; about 96 KiB at a 256 MiB guest and 10 MiB at 20 GiB). A free fails past 65535 sharers — impossible under 0030a's capacities (64 processes x 64 regions). `deallocate` decrements: a frame is recycled only when its count reaches zero (memory.rs:318-340's state rules otherwise unchanged), and a fresh allocation starts at 1. `enable_recycling` sets count 1 for every frame it marks ALLOCATED (memory.rs:294-296), so the boot test frames still free (main.rs:111-114). A new `share(frame) -> Result<(), FrameError>` increments; the frame must be ALLOCATED — METADATA or free frames are rejected. `deallocate_contiguous` requires count 1 on every page of a run, checked in its existing validation pass (memory.rs:349-386); the contiguous self-test builds a private count array (memory.rs:566-578). Sharing adds no stale-free detection: memory.rs:317's "cannot detect a stale free after reuse" stays true, and sharers track their own references (0025, the loader v2). Every current allocation site keeps count 1; sharing arrives with those specs. Rationale: the array is cheap, reserved once, and needs no locking beyond today's BSP+IF=0 rule. Rejected alternative: u8 (one shared frame can hold thousands of mappings once 0025 lands). | proposed |
| 0054-D2 | Per-process memory limits. Each process entry (0030-D1) carries its OOM class and its reserved/committed limits, set at spawn. The class derives from its CpuPolicy (userspace.rs:214-220, set at :550, :1220-1221, :1481, :1979): Desktop and Shell are protected, Application is normal, Agent is agent, and init's probes keep normal-equivalent limits (a test-class mapping, so the battery's limit assertions at init main.rs:170-171 and :395-404 hold unchanged). 0052 must keep this CpuPolicy-to-class mapping when it replaces the policy table. The class table (values are open question 3): protected is bounded only by the reserve; normal is lifted above 32 MiB (the Phase 1 exit commits 256 MiB in one process); background is not below normal (S18 orders kills, it does not cap background work); agent matches normal until grants land. vm-protocol's RESERVED_LIMIT/COMMITTED_LIMIT constants become the documented defaults the table starts from; SYS_VM_STATS reports the reading process's own values (userspace.rs:3316-3336; this is S6's vm-protocol-limit scope, and the ABI shape is unchanged). Enforcement applies the process's own limits at reserve and commit (vm.rs:190-193, :411-413). Limits are set at spawn and not adjusted at runtime in this spec (no syscall; grants land in Phase 2). Rejected alternative: keep the global constants (a runaway app gets the shell's headroom, and I6's multi-GB process never fits). | proposed |
| 0054-D3 | The reserve and the victim order. The reserve is a free-frame floor — open question 2 sizes it (a fixed MiB, a fraction of usable frames, or the smaller of the two) — fixed once at a point identical in every flavor, before the first session, and printed once as `MIRROR_MEM_RESERVE frames=<n>` (every flavor, content-free; common.ps1 recomputes it from MIRROR_FRAME_POOL's total= and the margin rule). `FrameAllocator::allocate` stays the kernel's own call and may draw the reserve; `allocate_for(class)` refuses to cross the floor for a non-protected class. Site map: page tables inside materialize, an app's image and stack in create_process, pixels (windows.rs:31-58), 0050's stack builds and DMA use the requester's class (an app's create is requested by the shell for the app's class); heap growth and the kernel's own mappings use the kernel's call (heapv2-D1's preflight counts the reserve as available to the kernel). Victim selection runs whenever a frame allocation fails for lack of frames — at the floor or at zero, never only at global exhaustion: first trim 0050's stack pool (under its prepare_kernel_update rule); then, for a non-protected requester, consider only victims of a strictly lower kill class (S18's order: background below agent below normal), and for a protected or kernel requester, every non-protected class; within a class, the largest committed plus charged frames, then the newest PID. A kill finishes the victim at once in the completion context — Outcome::OutOfMemory, threads unlinked (0030-D2), handles closed, its address space destroyed immediately (the victim is never running: the scheduler is BSP-only with IF=0 until 0051) — and its zombie keeps only the Outcome for validation (0030-D5); then the failed allocation retries once per kill, bounded, stopping at success or when no candidate remains. record_fault's self-kill (userspace.rs:1034-1039) is the last resort: with no candidate left, a protected process's failed fault still kills it, the shell session then ends, its children end SessionEnded and the console starts (0030-D5). Only a failed frame allocation triggers selection: the VM_RESERVE/RELEASE/PROTECT ENOMEM sites (userspace.rs:1012) take no frames and never run it, and create_process's failure (userspace.rs:1439) selects only when it gains a distinct frame-exhaustion error. Rejected alternative: kill the requester always (today's behavior — a background hog then outlives a normal app, against S18). | proposed |
| 0054-D4 | Markers and scripts. `MIRROR_FRAME_POOL` stays where it is (main.rs:186-193; 0019's sampler cites its position) and gains `refcount_meta=<bytes>`; common.ps1 gains a closed-world check that recomputes refcount_meta from total=. `MIRROR_MEM_RESERVE frames=<n>` joins test.ps1's Default and Trace `$required` lists (test.ps1:35, :39) and is checked exactly once with its full field list in run.ps1 and capture.ps1 (the MIRROR_SMP_READY pattern). `MIRROR_OOM_KILL class=<class> pid=<n>` prints per victim kill (flavor gating per open question 5); run.ps1 asserts it only in the OomOrder case and rejects it in every other scenario. Outcome::OutOfMemory maps to `reason=oom` in MIRROR_APP_RECLAIMED and the shell's state/detail read (userspace.rs:1503-1511) and in the desktop/agent cleanup lines (:1385-1404). Rationale: the OOM kill is a lifecycle event the owner must be able to see (S17's log follows in Phase 3), and the reserve is a boot-time contract the scripts can recompute. | proposed |

## Interfaces
- `kernel/src/memory.rs`: the refcount array (init in `enable_recycling`; `allocate`/`deallocate`/`allocate_contiguous_dma32`/`deallocate_contiguous` maintain it), `share`, `allocate_for(class)` and the reserve floor.
- `kernel/src/vm.rs`: the per-process limits at :190-193 and :411-413. The one-span bound at :398 stays on a fixed transaction cap (a new MAX_MATERIALIZE_BYTES equal to today's 256 MiB), because the rollback bitmap is a fixed 8 KiB stack array (vm.rs:12, :401); resident work stays non-preemptible (vm.rs:3-4), which larger limits make longer.
- `kernel/src/sched.rs` (0030a): the entry carries class and limits; victim selection, the kill/reap split and the retry run in the scheduler's completion context.
- `kernel/src/userspace.rs`: spawn sites set the class from CpuPolicy; the frame-failure sites (:1034-1039, :1058-1062, :1440-with-distinct-error) route through victim selection; :1012 is unchanged.
- `kernel/src/main.rs`: the reserve is fixed before the first session (one point, every flavor) and prints there; `MIRROR_FRAME_POOL` gains its field in place.
- `crates/vm-protocol/src/lib.rs`: the two constants are documented as the defaults the class table starts from; the encode/decode is unchanged. Host tests follow.
- `userspace/init`: the battery keeps normal-equivalent limits; the class-limit checks (test 3) and the OOM battery (test 4) live in the OomOrder scenario's session.
- `kernel/src/boot.rs` and `main.rs`: the `oom-order` token and SmokeMode, beside the existing modes.
- Scripts: run.ps1 gains `-Fault OomOrder` (ValidateSet, `$testMode`) with the OOM_KILL assertion; test.ps1 adds the case in both profiles plus the `-MemoryMiB 1024` commit case (the Phase 1 exit); common.ps1 gains the FRAME_POOL check; capture.ps1's absent list follows D4.
- readme.md: the pool paragraph (:307) and the fault-behavior lines (:317, the -12 row at :535), in the same commit.

## Acceptance tests
1. The existing battery and every frame-baseline check pass unchanged: all current allocations hold count 1, and the refcount metadata is METADATA, not allocated_frames, so no session delta exists (0050-D2's shared rule sees none).
2. Refcount self-tests (boot-smoke, beside memory.rs's existing tests): share then free both references in either order, recycling exactly at zero; a 65536th share fails; a contiguous run with any count above 1 is rejected before any change; `enable_recycling`'s prefix frames hold count 1 (the main.rs:111-120 checks).
3. Class limits, in the OomOrder scenario's session (or the shell session): a background probe and a normal probe report their own limits through SYS_VM_STATS, and each fails at its own bound and not the other's. Init's battery keeps its normal-equivalent limits and passes unchanged.
4. `-Fault OomOrder` (`mirror.test=oom-order`): the scenario seeds a session with a background victim, a normal requester and a protected process, shrinks a kernel-wide frame budget only in that case, and asserts: the background process dies with Outcome::OutOfMemory, `MIRROR_OOM_KILL class=background` prints exactly there, the requester's retry succeeds after the kill, the reserve holds, and the protected and normal processes survive. The scenario is excluded from validate_process's battery checks (userspace.rs:2212). This is the Phase 1 exit's OOM case (roadmap-replan.md:138).
5. Reserve: an allocation drive reaches the floor; a normal-class `allocate_for` fails there while the kernel's own `allocate` still succeeds; `MIRROR_MEM_RESERVE frames=` matches the recomputed value.
6. The Phase 1 exit's commit case: a new test.ps1 case boots `-MemoryMiB 1024` and has one normal process commit 256 MiB (past the old constant), with frame counts restored afterwards (0050-D2's rule).
7. Before merge (P8): the full `scripts/test.ps1` in debug and release, plus `-AgentDemo` while the agent-demo feature exists (RS6). The marker changes land in the same commit.

## Open questions (for Cameron, with the reviewer's recommendations)
1. When a normal app reaches the reserve, does victim selection run (background, then agent) before the app fails? Recommended: yes (this spec's D3).
2. Reserve size: a fixed MiB floor, a fraction of usable RAM, or the smaller of the two. Does the kernel draw from it? Recommended: min(fixed, fraction) as a free floor; the kernel may draw (D3).
3. The class limit table. Recommended: normal above 32 MiB commit (roadmap-replan.md:58 and the 256 MiB exit), background not below normal (S18, I6), protected bounded by the reserve.
4. Refcount width. Recommended: u16 (a u8 fails at 256 sharers, reachable under 0030a's 64x64 once 0025 lands).
5. Should `MIRROR_OOM_KILL` print in every flavor as a content-free lifecycle marker (S7b allows it)? Recommended: yes; then it leaves the `$forbidden` image lists and run.ps1 rejects it by scenario.
6. `Outcome::OutOfMemory` as a new variant with `reason=oom`? Recommended: yes.
7. Do charged kernel frames (page tables, surfaces, 0050's stacks) count toward limits or victim choice in Phase 1? Heap v2 and 0050 both defer this here.
8. Split 0054a into allocator-plus-limits and reserve-plus-OOM, and their numbers under RD24? The work order keeps the two halves as steps 1-2 and 3-4 either way.
9. RD6 (0054a carries the S18 reserve and OOM order) is due before Phase 1 and unconfirmed; confirm it with this spec.
10. Is init's Probe process "the background-class test process" of the Phase 1 exit, or does the OOM case get its own process and class (this draft: its own, per finding 3)?
