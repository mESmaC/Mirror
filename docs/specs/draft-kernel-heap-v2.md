# Kernel heap v2: demand-driven growth, slab caches, per-process frame charging

Status: draft (unnumbered NEW spec — roadmap-replan.md Phase 1 item 4; Cameron assigns the number per RD24, and the heapv2-Dn IDs below take it). Revised after claude's reviews of 58ed8cf.
Depends on: 0030a (its scheduler loop is a growth safe point, and charging attaches to its process entries, 0030-D1). Ordered after 0050 in Phase 1; no build dependency on 0050 — the heap window's leaf tables are already pinned at init (heap.rs:211, paging.rs:332-358), so growth maps into existing tables and needs no post-seal VA allocation.
Ledger: none directly (re-plan NEW spec). Related: S18 (the reserve and OOM order land in 0054a on top of this charging), S7/S7a/S7b (marker gating), RS1.

Line references are at HEAD 970e48c.

## Goal
The kernel heap stops being a fixed boot-sized arena. Today it is a first-fit free list (linked_list_allocator =0.10.6, kernel/Cargo.toml:16) at 1 MiB initial and 16 MiB maximum (heap.rs:28-31), grown only at two boot points in every flavor (main.rs:358, :383-388) plus boot-smoke's capacity test (main.rs:428), with no slab caching and no `alloc_error_handler` ("no allocation panics by design", heap.rs:126). Nothing heap-allocates at runtime, and no kernel memory is charged to a process. When this spec is done: growth is demand-driven at defined safe points up to the 16 MiB cap; small objects come from size-class slab caches; and kernel frames held on behalf of a process are charged to that process's table entry (0030-D1), so 0054a can limit them.

Why not growth inside `alloc` (claude's review blocker): `GlobalAlloc::alloc(&self, layout)` (heap.rs:128) cannot reach the frame allocator, the kernel page tables or the HHDM offset that `grow` needs (heap.rs:249-256) — both are `continue_boot` locals (main.rs:155-174) — the tables lent as `&`, the frame allocator as `&mut` — `PageTables` is deliberately !Send/!Sync (paging.rs:105-106), and a second `&mut FrameAllocator` made inside alloc would alias the caller's borrow. `grow`'s contract also requires the kernel root active, an exclusive frame allocator and no IRQ-needed lock held (heap.rs:243-248), which no arbitrary alloc caller can promise, and its shootdown wait briefly enables IRQs (heap.rs:155). So `alloc` never grows; growth is explicit at safe points that already meet the contract.

## Non-goals
- Per-process memory limits, the S18 fixed reserve and the OOM victim order (0054a); pressure notifications (0054b). This spec adds counters, never enforcement.
- Heap-byte charging and its API (`ChargedBox` or explicit charge/uncharge pairs): deferred to 0022, whose Phase 2 kernel objects are the first per-process heap consumers (no Phase 1 allocation could raise the counter). This spec charges frames only.
- Allocation on secondary CPUs (0051): the "only the BSP allocates" invariant (heap.rs:60-64) and the non-migrating HeapGuard are unchanged.
- A kernel VA allocator (0050) — see Depends on.
- Growth triggered from inside `alloc` (see Goal). The two boot growth points stay as pre-warming. Heap shrinking stays future work (readme.md:309): committed growth is permanent (heap.rs:6).
- The vm-protocol user-arena limits (0054a). Charging user image and stack frames is 0054a's limits decision, not this spec's.

## Decisions
| ID | Decision | Status |
| --- | --- | --- |
| heapv2-D1 | Demand-driven growth at safe points, never inside `alloc`. The heap tracks a low-water mark defined as the largest free block, measured under the lock by a probe `allocate_first_fit` immediately released (the crate's hole list is private, so this probe is how the mark and any layout fit are checked); a recorded shortfall that the probe says now fits is dropped without growth. The safe points — the top of 0030a's `sched::run` loop between dispatches and session seeding in main.rs, beside the two boot calls — each meet `grow`'s full contract: BSP, IF=0, kernel root active, `&PageTables`, `&mut FrameAllocator` and the HHDM offset in hand (the loops already hold all three, userspace.rs:609-617, :944), no IRQ-needed lock, and no syscall handler frame live. They run `heap::ensure(&tables, &mut frames, offset)`, which grows in 1 MiB steps (MAX_GROW_PAGES, heap.rs:31) while the largest block is below the mark, up to HEAP_MAX_SIZE. A failed allocation records its layout with `heap::note_shortfall(layout)`, called from `KernelAllocator::alloc` after its bound check (heap.rs:134-136), on a free-list miss, under the lock; the record keeps the largest pending layout, layouts compared by size + align − 1 (the feasibility rule's key); a slab refill miss records a page-sized one; the battery's deliberate failures record too, and test 1 clears them. A shortfall drives growth only when it can be satisfied: size + align − 1 must fit in the capacity still to be added (HEAP_MAX_SIZE − current size); an infeasible shortfall below the cap is dropped silently and leaves ensure armed. The free frame count (FrameStats, memory.rs:20-25) is preflighted before every growth, mark- or shortfall-driven — so a growth completes or never starts, and an infeasible request leaves the heap and frames unchanged. `alloc` is otherwise unchanged: on a free-list miss it returns null (heap.rs:137-139). A syscall whose allocation fails at the cap returns today's -12 (ENOMEM, the userspace.rs:1058-1062 pattern); readme.md:309's "handlers must not allocate" stays, and Phase 2's kernel-object allocation runs in the kernel-root deferred-completion path (the `State::Memory` pattern, userspace.rs:950-952), where a safe point can precede it. Interrupt contract: growth may briefly enable IRQs (heap.rs:155) only at these safe points, where no table or queue is half-updated; `alloc` never enables them. Every runtime allocation uses fallible APIs (`Vec::try_reserve*`, or raw `alloc` with a null check — stable 1.99.0 has no `allocator_api`, and infallible Box/Vec calls panic at the cap, against fail-closed). Rollback rules: a failed `alloc` changes nothing (it returns null before any heap change); a failed growth step rolls back only its uncommitted batch (heap.rs:291-297); steps committed earlier stay, because pre-growth is best effort, not one operation; and nothing is ever withdrawn — linked_list_allocator 0.10.6 cannot retract a committed tail, and unmapping it could free live blocks (open question 5). Failure policy: `ensure` stops at the first failed step (every loop is bounded). LimitExceeded means the heap is at HEAP_MAX_SIZE with growth still needed; it never re-arms (nothing can change at the cap). OutOfFrames and the pre-publication paging errors re-arm only when allocated_frames drops below its post-rollback value at the failure. Cancelled, Busy and InvalidContext are injection- or bug-class and never occur at a correct safe point; if one occurs, ensure marks it and never re-arms for the boot. Injected failures (test 5) neither print nor arm the back-off, and the injection static counts each use so a skipped attempt fails the test. A repeated shortfall no larger than the failed one does not re-arm. While a configured AP is missing, growth stays fail-closed: the transport check (smp.rs:785-786) runs before any frames are acquired (ensure calls `prepare_kernel_update`, smp.rs:787, and drops the result; map_heap_pages runs it again, paging.rs:384-385, with the existing rollback), and the back-off covers the boot. Failures print nothing; the one expected record is test 2's, printed by `capacity_self_test` itself (boot-smoke only) when its final `ensure` reports LimitExceeded (D4). `ensure` prints each `MIRROR_HEAP_GROWN phase=auto` record, from its own format string. No frame-allocator or paging signatures change. heap.rs:7's and :241's comments stay true under this design and are not touched; readme.md:7, :299 and :309 are updated in the same commit. Rationale: Phase 2's kernel objects need runtime allocation, and 0054a's dynamic limits consume D3's counters — both want this spec's mechanisms. Rejected alternative: growth inside `alloc` (blocked, see Goal). | proposed |
| heapv2-D2 | Slab caches for small objects: a layout is routed to a slab only when `layout.align() <= class_size`, with the class = max(size, align) rounded up to a power of two over 16 through 2048 bytes; everything else keeps first-fit on the free list (so the battery's 71-byte-at-32768-alignment case, heap.rs:695-706, still passes). Each cache is a list of arena pages with a per-page free list. A slab page whose objects are all free returns to the free list, so coalescing (heap.rs:756-761) is unchanged. Rationale: Phase 2's kernel objects are small and churn; first-fit alone fragments the arena over a session. Rejected alternative: per-type caches (couples the allocator to object types; size classes cover them). | proposed |
| heapv2-D3 | Per-process frame charging, frames only. The process entry (0030-D1) gains a kernel-frames counter, and the entry derives its page-table charge from its address space's `owned_table_count` (paging.rs:877-878) — so paging.rs does not change, and the many ownerless roots (hardening.rs:432, heap.rs:455, kernel_vm.rs:146, userspace.rs:439, vm.rs:643 and the tests) stay uncharged. Surface pixel frames (SURFACE_PAGES = 120 per app, windows.rs:15-17) are charged to the *shell's* entry, which owns the Application object and closes it: charged in `launch` after `Application::new` (userspace.rs:1453) and released in both destroy paths (the launch rollback at :1461 and close at :1570); an app's reclaim leaves the Application in its slot (:1516-1519), so the charge must live where reap follows every close (:2116-2132), and a faulted app with an open window leaves no dangling charge. `windows::self_test`'s Application (windows.rs:394, created before the shell process exists, userspace.rs:1965-1969) is uncharged. Exempt here: 0050's per-thread kernel stacks (0050-D2 keeps them uncharged global memory; whether to charge them is 0054a's call, with 256 frames per process at capacity). Uncharged: the kernel hierarchy's own tables, boot and global allocations (the BSP/AP stacks, the 0030a tables, DMA). Charged on allocation, released on free, asserted back to zero at reap (0030-D5); the zero-at-reap check runs in boot-smoke builds only, and in other flavors the counters are merely maintained (S7: a normal boot never panics on a test outcome). No limit is enforced anywhere in this spec. Rationale: S18 accounting needs the numbers before 0054a can set limits. | proposed |
| heapv2-D4 | Observability. `MIRROR_HEAP_GROWN` (main.rs:544) gains `phase=auto` for safe-point growths, printed from its own format string in test-trace and boot-smoke builds only (a default build grows silently: a mid-session growth marker could land in the hygiene probe's no-serial window, capture.ps1:367-376; the boot and after_userspace records still print in every flavor). In smoke boots an auto record can precede the after_userspace record, because the init sessions are safe points (0030-D1). Assert-MirrorHeapGrowth (common.ps1:744-832, including its per-phase GROW_TESTS ordering at :790-797) is rewritten: the hard-coded 2 MiB/3 MiB sizes are dropped; starting from MIRROR_HEAP_READY's size, the check walks every GROWN line in order requiring size = previous + added_pages×4096 and free = size − used, with exactly one `boot` and one `after_userspace` record in order, at most 13 `auto` records, and the full field list on every record. The literal `phase=auto` joins test.ps1's Default `$forbidden` image-scan list, proving a default kernel cannot print it. Injected test-5 failures print no record. Exactly one `MIRROR_HEAP_GROW_SKIPPED phase=auto reason=LimitExceeded` record is expected per smoke boot that reaches capacity_self_test, printed before `MIRROR_HEAP_LIMIT_OK`; every other boot has none (closed-world). `MIRROR_HEAP_CHARGE_OK tables_peak=<n> surfaces_peak=<n>` is boot-smoke only, prints once per session drain — three lines per smoke boot with a desktop session, two without one (-NoDisplayDevice/-NoKeyboard, run.ps1:672-676, main.rs:419-421) — with the session's peak charged frames, checked by exact count per scenario (the run.ps1:669 pattern). It joins both `$forbidden` lists (test.ps1:36, :40), run.ps1's `$markers` (run.ps1:520) and capture.ps1's absence list (capture.ps1:696). | proposed |

## Interfaces
- `kernel/src/heap.rs`: the probe-based largest-block mark, `heap::ensure` (which prints the `phase=auto` record) and `heap::note_shortfall`, called from `KernelAllocator::alloc` after the bound check on a free-list miss (D1), the slab caches (D2), and a boot-smoke-only injection static that `ensure` reads for test 5. HeapGuard, GrowthGuard and the existing fault-injection modes are unchanged. The session frame-check rule is 0050-D2's (the heap-growth term); this spec relies on it and does not add a second one.
- `kernel/src/paging.rs`: unchanged — the table charge is derived at the process entry from `owned_table_count` (paging.rs:877-878).
- `kernel/src/windows.rs` and `userspace.rs`'s ShellRuntime: surface frame charging at `launch` (userspace.rs:1453) and release at both destroy paths (:1461, :1570) (D3).
- `kernel/src/sched.rs` (0030a) and `userspace.rs`: the process entry's counter, the boot-smoke zero-at-reap check, and the safe-point calls (D1). `sched::run` keeps the loop's `&PageTables`, `&mut FrameAllocator` and HHDM-offset parameters so the safe points meet `grow`'s contract. The session frame-check rule (the heap-growth term; userspace.rs:776-780, :1334-1338, :2133-2137, 0030-D5's per-session check) is 0050-D2's — this spec relies on it and adds nothing to it.
- `kernel/src/main.rs`: the two `grow_kernel_heap` calls stay; session seeding gains an `ensure` call before the session's frame snapshot (D1's other safe point); test 2 joins `capacity_self_test` at main.rs:428.
- `scripts/common.ps1`: the Assert-MirrorHeapGrowth rewrite (D4); `run.ps1` and `capture.ps1` lists for `MIRROR_HEAP_CHARGE_OK`; test.ps1's `$forbidden` lists gain `MIRROR_HEAP_CHARGE_OK` and the `phase=auto` literal. No boot.rs, fault-injection or test.ps1 case changes.
- readme.md:7, :299 and :309 (D1). heap.rs:7's and :241's comments stay true and are not touched.

## Acceptance tests
1. The existing heap battery passes: growth rollback and guards (`MIRROR_HEAP_GROW_TESTS_OK`), the 16 MiB limit and reclaim (`MIRROR_HEAP_LIMIT_OK`), coalescing, the cross-table paging checks (`MIRROR_HEAP_PAGING_OK`) and the interrupts test (`MIRROR_HEAP_IRQ_OK`), with its exhaustion and full-heap assertions (heap.rs:681-688, :703-706, :725, :743-745, :762, :780-783) intact; its deliberate failures leave shortfall records, which it clears. No growth guard is needed: `alloc` never grows, and `heap::self_test` runs at main.rs:273, before any safe point exists. In smoke boots the init sessions are safe points (0030-D1), so an auto record can precede the after_userspace record there; the rewritten ordered walk (D4) derives every size, so it holds. The end-of-boot `used == 0` invariant (heap.rs:587-672) is kept unchanged: with 0030a's tables in .bss, no persistent heap allocation exists for it to subtract.
2. Safe-point growth, mapped to the Phase 1 exit's heap-growth stress case: inside `capacity_self_test` (main.rs:428), whose direct `ensure` call is named a test-only safe point, a workload through the fallible APIs allocates past the current largest block; no allocation grows the heap; the failed request is recorded with `note_shortfall`, the safe point grows for it, and a retried allocation succeeds. Frame rule: `allocated_frames` rises by exactly the grown pages and nothing else (the heap.rs:607-610 pattern) — for the permanently grown heap this is how the exit's "frame counts restored afterwards" reads (open question 4). The cap is reached with feasible requests; a request that can never fit (over the remaining capacity) leaves `stats()` and `allocated_frames` unchanged both at the allocation and at the next safe point, and the one accepted `MIRROR_HEAP_GROW_SKIPPED phase=auto reason=LimitExceeded` record is printed by `capacity_self_test` itself (boot-smoke only) when its final `ensure` reports the heap at the cap with growth still needed, before `MIRROR_HEAP_LIMIT_OK`. A second boot-smoke step makes the relaunch pair's seeding `ensure` (named in main.rs) hold a heap block at the session's first loop top, so the *next* loop-top `ensure` grows mid-session; the session's drain check then runs under 0050-D2's shared rule with a nonzero delta, and the test asserts the delta is exactly 256 pages.
3. Slabs, inside `heap::self_test` before any persistent allocation: allocate/free cycles across every size class, including a large-alignment layout that must bypass the slabs (the heap.rs:695-706 pattern); pattern-check the bytes; every emptied slab page returns to the free list (proven by a full-heap allocation afterwards, the heap.rs:756-761 pattern).
4. Charging: across a process create/run/reap cycle (0030a's table) and a shell app launch/close, the app entry's page-table frames and the *shell* entry's surface frames (D3) rise and return exactly to zero, and `MIRROR_HEAP_CHARGE_OK` prints each session's peaks at its drain. The injection check is non-fatal and runs once per smoke boot at the *last* session's drain, whatever that session is (the shell session, or the relaunch pair when the desktop is skipped): a boot-smoke self-test deliberately leaks one charge, asserts that the reap check reports the error, repairs the counter, and only then prints the marker.
5. Failure injection: inside `capacity_self_test`, before the cap drive and with the held-memory workload keeping the largest block below the mark, the existing `FailFramesAfter`/`CancelBeforeCommit` modes (heap.rs:259-265) reach `ensure` through the injection static; the injected failures neither print nor arm the back-off, the static counts each use and the test asserts the count (so a skipped attempt fails), and the expected result is a stopped safe point with `stats()` and `allocated_frames` unchanged and the tail pages still unmapped (the heap.rs:474-490 pattern), with `ensure` stopped at the first failed step.
6. Before merge (P8): the full `scripts/test.ps1` in debug and release (plus `-AgentDemo` while the agent-demo feature exists, RS6). The marker script changes land in the same commit.

## Dependencies
No new crates. `linked_list_allocator =0.10.6` stays (the slab caches sit above it inside the same arena).

## Open questions
1. The spec number (RD24) and with it the decision-ID prefix.
2. The low-water mark value (a largest-block size; proposed: 256 KiB) and which future callers retry after a safe point vs fail immediately.
3. The size-class list (16-2048 by powers of two) and the slab page size (one 4 KiB arena page per slab page is proposed).
4. The Phase 1 exit's "each with frame counts restored afterwards" (roadmap-replan.md:133) cannot apply literally to a permanently grown heap (heap.rs:6); test 2 reads it as "no frames beyond the grown capacity". Confirm or reword the exit.
5. Shrinking the heap needs an allocator that can retract its top: linked_list_allocator 0.10.6 cannot (its `extend` merges the tail into the free list, and its hole list is private), and `unmap_heap_pages` may never remove committed capacity (paging.rs:408-409). If Cameron wants shrink, it is a new decision: replace the allocator, or give the slab layer whole tail pages.
6. The alternative ordering "heap v2 after 0054a, with growth inside `alloc` once 0054a's frame-allocator rework can reach it from that context" is a live option for Cameron: 0054a lands in Phase 1 (roadmap-replan.md:124) before any Phase 2 consumer exists, so the reorder delays nothing in Phase 2; its cost is that 0054a's dynamic limits would land without D3's counters already running, and this spec's safe-point design works today without touching the frame allocator.
