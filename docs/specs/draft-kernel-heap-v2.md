# Kernel heap v2: demand-driven growth, slab caches, per-process frame charging

Status: draft (unnumbered NEW spec — roadmap-replan.md Phase 1 item 4; Cameron assigns the number per RD24, and the heapv2-Dn IDs below take it). Revised after claude's reviews of 58ed8cf.
Depends on: 0030a (its scheduler loop is a growth safe point, and charging attaches to its process entries, 0030-D1). Ordered after 0050 in Phase 1; no build dependency on 0050 — the heap window's leaf tables are already pinned at init (heap.rs:211, paging.rs:332-358), so growth maps into existing tables and needs no post-seal VA allocation.
Ledger: none directly (re-plan NEW spec). Related: S18 (the reserve and OOM order land in 0054a on top of this charging), S7/S7a/S7b (marker gating), RS1.

Line references are at HEAD 970e48c.

## Goal
The kernel heap stops being a fixed boot-sized arena. Today it is a first-fit free list (linked_list_allocator =0.10.6, kernel/Cargo.toml:16) at 1 MiB initial and 16 MiB maximum (heap.rs:28-31), grown only at two boot points in every flavor (main.rs:358, :383-388) plus boot-smoke's capacity test (main.rs:428), with no slab caching and no `alloc_error_handler` ("no allocation panics by design", heap.rs:126). Nothing heap-allocates at runtime, and no kernel memory is charged to a process. When this spec is done: growth is demand-driven at defined safe points up to the 16 MiB cap; small objects come from size-class slab caches; and kernel frames held on behalf of a process are charged to that process's table entry (0030-D1), so 0054a can limit them.

Why not growth inside `alloc` (claude's review blocker): `GlobalAlloc::alloc(&self, layout)` (heap.rs:128) cannot reach the frame allocator, the kernel page tables or the HHDM offset that `grow` needs (heap.rs:249-256) — both are `continue_boot` locals lent out as `&mut` (main.rs:155-174), `PageTables` is deliberately !Send/!Sync (paging.rs:105-106), and a second `&mut FrameAllocator` made inside alloc would alias the caller's borrow. Growth also briefly enables IRQs during its shootdown (heap.rs:155-156), which no arbitrary alloc caller may do. So `alloc` never grows; growth is explicit at safe points that already hold these values.

## Non-goals
- Per-process memory limits, the S18 fixed reserve and the OOM victim order (0054a); pressure notifications (0054b). This spec adds counters, never enforcement.
- Heap-byte charging and its API (`ChargedBox` or explicit charge/uncharge pairs): deferred to 0022, whose Phase 2 kernel objects are the first per-process heap consumers (no Phase 1 allocation could raise the counter). This spec charges frames only.
- Allocation on secondary CPUs (0051): the "only the BSP allocates" invariant (heap.rs:60-64) and the non-migrating HeapGuard are unchanged.
- A kernel VA allocator (0050) — see Depends on.
- Growth triggered from inside `alloc` (see Goal). The two boot growth points stay as pre-warming. Heap shrinking stays future work (readme.md:309): committed growth is permanent (heap.rs:6).
- The vm-protocol user-arena limits (0054a). Charging user image and stack frames is 0054a's limits decision, not this spec's.

## Decisions
| ID | Decision | Status |
| --- | --- | --- |
| heapv2-D1 | Demand-driven growth at safe points, never inside `alloc`. The heap tracks a low-water mark; the safe points — the top of 0030a's `sched::run` loop between dispatches and session seeding, both with the kernel root active, IF=0, the frame allocator in hand and no IRQ-needed lock held, beside the two boot calls — run `heap::ensure(&tables, &mut frames, offset)`, which grows in 1 MiB steps (MAX_GROW_PAGES, heap.rs:31) while free space is below the mark, up to HEAP_MAX_SIZE. `alloc` is unchanged: on a free-list miss it returns null (heap.rs:137-139). No frame-allocator or paging signatures change, and nothing here is 0054a's to replace. Interrupt contract: growth may briefly enable IRQs (heap.rs:155-156) only at these safe points, where no table or queue is half-updated; `alloc` never enables them. Every runtime allocation uses fallible APIs (`Vec::try_reserve*`, or raw `alloc` with a null check — stable 1.99.0 has no `allocator_api`, and infallible Box/Vec calls panic at the cap, against fail-closed). Growth is watermark-driven and unattributable to any single allocation, so there is nothing per-demand to roll back; a failed growth step rolls back its uncommitted batch as today (heap.rs:291-297), and an infeasible request (one the tail free block plus the remaining capacity cannot hold, with alignment padding) never triggers growth. heap.rs:7's and :241's "never implicitly grows" comments and readme.md:7, :297 and :299-303 are updated in the same commit. Rationale: Phase 2's kernel objects need runtime allocation long before 0054a lands. Rejected alternatives: growth inside `alloc` (blocked, see Goal); sequencing after 0054a (the reach problem is layering, not frames, and 0054a does not change it). | proposed |
| heapv2-D2 | Slab caches for small objects: a layout is routed to a slab only when `layout.align() <= class_size`, with the class = max(size, align) rounded up to a power of two over 16 through 2048 bytes; everything else keeps first-fit on the free list (so the battery's 71-byte-at-32768-alignment case, heap.rs:695-706, still passes). Each cache is a list of arena pages with a per-page free list. A slab page whose objects are all free returns to the free list, so coalescing (heap.rs:756-761) is unchanged. Rationale: Phase 2's kernel objects are small and churn; first-fit alone fragments the arena over a session. Rejected alternative: per-type caches (couples the allocator to object types; size classes cover them). | proposed |
| heapv2-D3 | Per-process frame charging, frames only. The process entry (0030-D1) gains a kernel-frames counter. Charged: user page-table frames (`UserAddressSpace::allocate_table`, paging.rs:1385-1400, and its release paths paging.rs:1072, :1362, :1439 — today's `owned_tables` count, paging.rs:820, becomes the charge) and the application surface pixel frames (SURFACE_PAGES = 120 frames per app, windows.rs:15-17, reclaimed at close, userspace.rs:1566-1574), the largest per-process kernel allocation. Uncharged: the kernel hierarchy's own tables (`PageTables::allocate_table`, paging.rs:739-747), boot and global allocations (stacks, the 0030a tables, DMA). Charged on allocation, released on free, asserted back to zero at reap (0030-D5); the zero-at-reap check runs in boot-smoke builds only, and in other flavors the counters are merely maintained (S7: a normal boot never panics on a test outcome). No limit is enforced anywhere in this spec. Rationale: S18 accounting needs the numbers before 0054a can set limits. | proposed |
| heapv2-D4 | Observability. `MIRROR_HEAP_GROWN` (main.rs:544) gains `phase=auto` for safe-point growths, printed in test-trace and boot-smoke builds only (a default build grows silently: a mid-session growth marker could land in the hygiene probe's no-serial window, capture.ps1:367-376; the boot and after_userspace records still print in every flavor). Assert-MirrorHeapGrowth (common.ps1:752-790) is rewritten: starting from MIRROR_HEAP_READY's size, walk every GROWN line in order requiring size = previous + added_pages×4096 and free = size − used, with exactly one `boot` and one `after_userspace` record in order, at most 13 `auto` records, and the full field list on every record. `MIRROR_HEAP_CHARGE_OK tables=<n> surfaces=<n>` is boot-smoke only, printed once per session drain after the charge check; it joins run.ps1's `$markers` (run.ps1:520) and capture.ps1's absence list (capture.ps1:696). No test.ps1 image-list change is needed: the GROWN string already appears in every flavor. | proposed |

## Interfaces
- `kernel/src/heap.rs`: the low-water mark and `heap::ensure` (D1), the slab caches (D2), and a boot-smoke-only injection static that `ensure` reads for test 5. KernelAllocator, HeapGuard, GrowthGuard and the existing fault-injection modes are unchanged.
- `kernel/src/paging.rs`: `UserAddressSpace::allocate_table` and its release paths charge the owning process (D3); `PageTables::allocate_table` stays uncharged.
- `kernel/src/windows.rs` and `userspace.rs`'s ShellRuntime close: surface frame charging (D3).
- `kernel/src/sched.rs` (0030a): the process entry's counter, the boot-smoke zero-at-reap check, and the safe-point calls (D1).
- `kernel/src/main.rs`: the two `grow_kernel_heap` calls stay; test 2 joins `capacity_self_test` at main.rs:428.
- `scripts/common.ps1`: the Assert-MirrorHeapGrowth rewrite (D4); `run.ps1` and `capture.ps1` lists for `MIRROR_HEAP_CHARGE_OK`. No boot.rs, fault-injection or test.ps1 case changes.
- readme.md:7, :297, :299-303 and :309, and heap.rs:7/:241's comments (D1).

## Acceptance tests
1. The existing heap battery passes: growth rollback and guards (`MIRROR_HEAP_GROW_TESTS_OK`), the 16 MiB limit and reclaim (`MIRROR_HEAP_LIMIT_OK`), coalescing, the cross-table paging checks (`MIRROR_HEAP_PAGING_OK`) and the interrupts test (`MIRROR_HEAP_IRQ_OK`). Its exhaustion and full-heap assertions (heap.rs:681-688, :703-706, :725, :743-745, :762, :780-783) run with growth disabled through a boot-smoke `heap::without_growth` guard, so their null-result and baseline expectations hold; the script's boot=2 MiB / after_userspace=3 MiB sizes are preserved because no auto growth can precede them (the first safe point is after main.rs:388). The end-of-boot `used == 0` invariant (heap.rs:587-672) is kept unchanged: with 0030a's tables in .bss, no persistent heap allocation exists for it to subtract.
2. Safe-point growth, mapped to the Phase 1 exit's heap-growth stress case: inside `capacity_self_test` (main.rs:428), a workload through the fallible APIs allocates past the current free space; no allocation grows the heap; at the next safe point the heap grows and a retried allocation succeeds. Frame rule: `allocated_frames` rises by exactly the grown pages and nothing else (the heap.rs:607-610 pattern) — for the permanently grown heap this is how the exit's "frame counts restored afterwards" reads (open question 4). An infeasible request (over the cap) leaves `stats()` and `allocated_frames` unchanged. Growth to the cap then refuses cleanly: null, no panic.
3. Slabs, inside `heap::self_test` before any persistent allocation: allocate/free cycles across every size class, including a large-alignment layout that must bypass the slabs (the heap.rs:695-706 pattern); pattern-check the bytes; every emptied slab page returns to the free list (proven by a full-heap allocation afterwards, the heap.rs:756-761 pattern).
4. Charging: across a process create/run/reap cycle (0030a's table) and a shell app launch/close, the entry's kernel frames (page tables; surfaces) rise and return exactly to zero, and `MIRROR_HEAP_CHARGE_OK` prints its fields. The injection check is non-fatal: a boot-smoke self-test deliberately leaks one charge, asserts that the reap check reports the error, repairs the counter, and only then prints the marker.
5. Failure injection: the existing `FailFramesAfter`/`CancelBeforeCommit` modes (heap.rs:259-265) pass against `ensure` through the injection static; the expected result is a null-yielding safe point with `stats()` and `allocated_frames` unchanged and the tail pages still unmapped (the heap.rs:474-490 pattern).
6. Before merge (P8): the full `scripts/test.ps1` in debug and release (plus `-AgentDemo` while the agent-demo feature exists, RS6). The marker script changes land in the same commit.

## Dependencies
No new crates. `linked_list_allocator =0.10.6` stays (the slab caches sit above it inside the same arena).

## Open questions
1. The spec number (RD24) and with it the decision-ID prefix.
2. The low-water mark value (proposed: 256 KiB free) and which future callers retry after a safe point vs fail immediately.
3. The size-class list (16-2048 by powers of two) and the slab page size (one 4 KiB arena page per slab page is proposed).
4. The Phase 1 exit's "each with frame counts restored afterwards" (roadmap-replan.md:133) cannot apply literally to a permanently grown heap (heap.rs:6); test 2 reads it as "no frames beyond the grown capacity". Confirm or reword the exit.
