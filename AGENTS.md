## Goal and decisions
Mirror is an agent harness that is also a complete, fast, independent x86_64 operating system, written in Rust plus assembly. It boots through UEFI and Limine. VMware is the VM target for daily use and development, and QEMU runs the automated tests. VirtualBox is not a target.
- Goal and v1 definition: `docs/specs/0000-north-star.md`.
- Decision ledger: `docs/specs/decisions.md`. It is authoritative.

## Build
Run commands from the repository root in PowerShell.
- `.\scripts\build.ps1 [-Release] [-Trace] [-Smoke]` builds the three userspace programs (init, the desktop shell and the app) and the kernel and stages `build\esp\`. It then builds the host tool `tools\mirror-image`, which writes the disk image `build\mirror.img` and its VMDK descriptor `build\mirror.vmdk` from that tree and verifies the image, so the build needs the MSVC linker and Windows SDK. `-Trace` and `-Smoke` enable the kernel features `test-trace` and `boot-smoke`.
- `.\scripts\package.ps1 [-Release] [-Perf <items>]` runs a default-flavor build. Without `-Perf` it copies the image and descriptor to `build\dist\`. `-Perf` validates the required item list before building, copies the staged ESP privately, adds exactly that `mirror.perf=` token and requests 1920x1080, then writes and verifies `build\dist\perf\mirror.img` and `mirror.vmdk`. The kernel and all module SHA256 values must match daily staging; the daily config and `build\dist\` package stay unchanged. VMs use only the packaged copies.
- `package.ps1 -Lane [-Release] -LaneRoot <path> -LockOwner <nick/task>` invokes the std-only `tools/perf-probe` controller. It takes its own machine lease, exports a clean committed tree outside all checkouts, builds offline with the pinned toolchain and a config-free cached Cargo home, and publishes `build/dist/mirror.package.json` last. Optional `-CargoHome` and `-LimineArchive` name existing caches; no downloads. `-LaneSlot qemu|qemu2` restricts acquisition to that slot with no fallback. Lane packages are tokenless default flavor, so `-Perf` is rejected. Every packaging mode invalidates old provenance before replacing either artifact. Only a matching LaneRoot `finalized-valid` record makes a lane package usable. See `docs/lane-recovery.md`.
- `package.ps1 -Lane -Recover <package-id> -LaneRoot <path> -LockOwner <nick/task>` checks controller/worker identities and the old job before cleaning an interrupted export; it never resumes building or publishes partial output. Run it from your own current checkout. `scripts/vmrun.ps1` accepts the planned case/recovery interface but **both VMware cases and VMware recovery are disabled** until 0015d D11 evidence; host fixtures cannot enable them.
- `mirror-image disk --esp <dir> --out <img> --vmdk <vmdk> [--perf]` accepts `--perf` once, without a value, only on `disk`. It selects CID `50455246` instead of daily CID `4d495252`; complete descriptor validation checks the header, parent CID, one flat extent, geometry and disk database, rejecting missing, duplicate or extra fields. Performance and daily snapshot chains are separate. `verify --esp <dir> <img>` reads back the image against the staged tree.
- `-Perf <items>` on package, run and capture accepts the case-sensitive items `boot`, `1`, `mem`, `burn`, `flip`, `telemetry`, `agent`, comma-separated without empty or repeated items. `mem,1` and `burn` without `1` are invalid; the complete ASCII `mirror.perf=` token is at most 64 bytes. Every valid token enables milestones; `mem` and `1` enable memory samples, while unavailable input/burn and reserved slices emit explicit skips. Bare `-Perf`, unknown items and malformed combinations fail before a build or boot (spec 0019a).
- The ledger (S7a) defines three kernel flavors: default (clean, for daily use), `test-trace` (adds test serial markers, for captures) and `boot-smoke` (`test-trace` plus the self-test and fault battery). Only `boot-smoke` runs init's test battery and the test-fixture checks; default and trace kernels start the shell directly.
- Trap: `.cargo\config.toml` links every `x86_64-unknown-none` crate with `kernel\linker.ld` and forces frame pointers, which the kernel's crash backtrace walks; `kernel\linker.ld` also defines the `.text` bounds that the walk checks return addresses against (spec 0051). `build.ps1` overrides these flags per program through `CARGO_ENCODED_RUSTFLAGS`: the program's own `userspace\<pkg>\linker.ld`, the small code model, and release LTO off, with no forced frame pointers. Never build userspace with `cargo build --workspace` or `cargo build -p mirror-<pkg>`: the images come out wrongly linked. `cargo check` and `cargo clippy` are safe because they do not link.
- Use Rust 1.99.0, pinned in `rust-toolchain.toml`. `build.ps1` and `test.ps1` first run the `Assert-MirrorToolchain` preflight (`scripts\common.ps1`). It fails unless `rustc --version` reports the pinned version and the workspace `rust-version` in `Cargo.toml` is its major.minor, because a `RUSTUP_TOOLCHAIN` variable, a `rustup override` or another `rustc` on `PATH` silently replaces the pin. Change the pin only in a dedicated bump commit that changes both values, following the bump procedure in spec 0011. The same commit changes the `rust-version` of each `tools\` workspace, which the preflight does not read.

## Test
- `.\scripts\test.ps1` is the full suite: rustfmt `--check`, host unit tests, and clippy `-D warnings` with no features, with `--features test-trace` and with all features, plus rustfmt, host tests and clippy for `tools\mirror-image` and `tools\perf-probe`, and PowerShell entry fixtures. Then, for debug and for release: a smoke build and every smoke boot, which must leave `build\mirror.img` byte-identical; a trace build and its normal-boot captures, absolute and then `-RelativePointer`; a default build; a binary scan of the trace and default `kernel.elf` for strings each flavor must or must not contain; and the hygiene capture. It takes about 20 minutes and stops at the first failure.
- Host tests need an explicit target because the default target is bare metal: `cargo test --locked -p <crate> --target x86_64-pc-windows-msvc`. This needs the MSVC build tools. The `crates\` packages, `tools\mirror-image` and `tools\perf-probe` have host tests. The latter includes synthetic Windows job/lease/controller tests, with no VMware operation. `scripts/test-lane.ps1` tests the actual PowerShell entries with synthetic package files; `test.ps1` runs it with inbox PowerShell 5.1.
- `mirror-perf-protocol` host tests cover the allocation-free token parser, counter arithmetic and exact marker schemas. `test.ps1` runs them and checks PERF markers as a closed family; tokenless smoke boots and captures reject every `MIRROR_PERF_` line.
- The `tools\` workspaces are host-only and excluded from the root workspace, so `cargo fmt --all`, `clippy --workspace` and `cargo test -p` never reach them. Run each one's fmt, clippy and host tests through `--manifest-path`, with `--locked --target x86_64-pc-windows-msvc` (fmt takes neither): `cargo fmt --all --manifest-path tools\mirror-image\Cargo.toml -- --check`, `cargo clippy --locked --all-targets --target x86_64-pc-windows-msvc --manifest-path tools\mirror-image\Cargo.toml -- -D warnings` and `cargo test --locked --target x86_64-pc-windows-msvc --manifest-path tools\mirror-image\Cargo.toml`.
- Run those same three commands with `tools\perf-probe\Cargo.toml` for the host lane. `test.ps1` includes both host workspaces before the QEMU cases.
- One boot: `.\scripts\run.ps1 -Smoke [-Release] [-DeviceProfile <V1|LegacyVirtio>] [-BaselineCpu] [-NoVmport] [-Fault <Name>]`. `V1`, the default, attaches the v1 devices: the AHCI test disk, an e1000 NIC, PS/2 and VGA. `LegacyVirtio` attaches the legacy VirtIO test disk instead, and the `Block*` faults need it. `-CrowdedPci` adds 32 PCIe root ports at VMware's slots on top of either profile (spec 0013). `-BaselineCpu` boots plain `qemu64`, without SMEP and SMAP, and `-ExtendedCpu` boots `max`; pass at most one (0016-D6). `-NoVmport` turns q35's `vmport` off, so the mouse stays relative (spec 0017c). `-PanicReboot` passes `mirror.panic=reboot` to a panic fault (spec 0051). Without `-Smoke` it boots interactively and never exits on its own (a guest reset, such as the console's `restart`, reboots it), so always pass `-Smoke`. Every boot uses the disk image, attached read-only, and `run.ps1` passes its Limine config, with any `mirror.test=` argument, as an SMBIOS string. Pass `-NoBuild` only if the staged kernel already matches the requested profile and features. Nothing checks this.
- `.\scripts\capture.ps1` builds a trace kernel (`build.ps1 -Trace`), boots it, drives it with QMP input and checks screenshots. With `-NoBuild` the staged kernel must be a trace build; without `MIRROR_TRACE_ON` the capture fails fast. It points with absolute vmmouse positions; `-RelativePointer` boots with `vmport=off` and moves the pointer by relative PS/2 motion. `capture.ps1 -NoBuild -Hygiene` instead probes a staged default kernel: no trace or init markers, no fixture checks, and no serial output after typing or pointer moves. Every ordinary capture, the hygiene probe included, ends by typing `restart` at the kernel console: QEMU must stop with one guest-reset SHUTDOWN event, and the hygiene probe allows only the two reset lines after that typing (spec 0058a). Hygiene waits for the 0029 dark launcher pixels before one Notes click, then waits up to `-TimeoutSeconds` for its start marker without retrying the click; update that readiness check if the launcher geometry or colors change.
- `run.ps1 -Perf <items>` and `capture.ps1 -Perf <items>` inject the validated token through a private SMBIOS Limine config, leaving the image unchanged. Ordinary capture remains trace. `capture.ps1 -PerfCapture -Perf <items> [-PerfScenario Markers] [-NoHpet]` builds default, uses pixel readiness, rejects trace/init output and caps each Markers run at 60 seconds excluding build. Markers sends no arming key and accepts no INPUT/WINDOW records. `-Hygiene` is mutually exclusive with performance options and remains tokenless; `-NoBuild` still requires the matching staged flavor.
- The 0019a full-suite additions are three smoke cases per debug/release profile (`-Perf 'boot,1,burn'`, `-Fault PageFault -Perf boot`, `-Fault PerfInvalid`) within the existing 30-second smoke cap, then two default Markers captures per profile: `-Perf mem` until three samples, and `-Perf '1,burn' -NoHpet` for 12 seconds with one initial `ns=none` sample and no periodic samples. The four Markers captures have a combined four-minute cap.
- Run the build, run, capture, package and test scripts one at a time, across all agents and terminals. Within one checkout they share `build\` (the staged ESP, the disk image `build\mirror.img`, `run.ps1`'s Limine config `build\limine-smbios.txt`, firmware variables, serial logs), so a second command silently corrupts the first. Across checkouts they share the machine's CPUs, whose load causes timing flakes, so at most two heavy runs go at once. So first take one of the two machine-wide run-lock slots: `New-Item -ItemType Directory C:\Users\engin\Desktop\Mirror-locks\qemu -ErrorAction Stop`, or `...\qemu2` if that fails (two heavy runs at once is the limit). It fails while someone else holds the lock: then stop and wait, and never overwrite or remove another owner's lock (if it looks stale, ask in xros_chat). Once it succeeds, write an `owner.txt` inside (nick, task, worktree, start time), and remove the folder when done. If your sandbox cannot delete the folder, release the lock by appending a line `released=<UTC time>` to `owner.txt` and saying so in xros_chat. Only the owner's own `released=` line makes its lock removable, and outside the lane tooling only Claude removes a released folder: it checks that `owner.txt` ends with the owner's `released=` line, deletes the folder and posts `lock free` in xros_chat. Agents using the manual protocol treat a released folder as busy and wait for that post. Manual takers never race to remove the same released folder. If Claude is unavailable, ask Cameron to remove it. The 0015c lane controller instead publishes release through its held owner handle after durable finalization, then records the release identity before closing. It can reclaim a released generation only by an identity-bound, no-replace rename to a unique sibling, record that detached artifact, and acquire a fresh lease; it never deletes at the shared acquisition path or reuses a released lease. Detached leftovers belong to the detacher and cannot block fresh acquisition. See `docs/lane-recovery.md` for crash recovery and the VMR-D6 named-replacement exception: Cameron must explicitly name the run/root, original and replacement operators and scope, with authorization persisted before acting. No age-based takeover or workaround for a blocked deletion is permitted. The same lock covers Mirror VMware boots and performance measurements. `cargo check`, clippy, fmt and host tests need no lock.
- Manual VM checks boot `build\dist\mirror.vmdk` from `package.ps1` in a VMware VM set up as `docs/vm-settings.md` records.
- QEMU and OVMF are found in `.tools\qemu\` or on `PATH`, or set through `QEMU_PATH`, `OVMF_CODE` and `OVMF_VARS`.
- A failed boot leaves its output in `build\serial.log` and `build\qemu.stderr.log`. `test.ps1` clears its log directory, `build\test-logs\`, when it starts, then copies in only passing cases, so after a failed run it holds just the cases that passed before the failure.

### When to test
- Before each commit, run the targeted cases for what it touches. `test.ps1` lists every case; copy the matching commands from it:
  - Any Rust change: `cargo fmt --all -- --check` and the three clippy commands. A change under `crates\` also runs that crate's host tests.
  - A change under `tools\`: that workspace's fmt `--check`, clippy `-D warnings` and host tests, through `--manifest-path` as above. A change to `crates\ext2-layout` also runs them for `tools\mirror-image`, which uses it.
  - Kernel or userspace code: `build.ps1 -Smoke`, then `run.ps1 -Smoke -NoBuild` with no `-Fault`, plus every case whose switches or `-Fault` name exercise the touched code (for example the `-Xhci` cases for xHCI code, or the `LegacyVirtio` cases for VirtIO block code). To find them, search `run.ps1` and `common.ps1` for the markers that code prints.
  - Desktop, console, input or display code: also `build.ps1 -Trace`, then `capture.ps1 -NoBuild -CpuCount 4` and `capture.ps1 -NoBuild -RelativePointer -CpuCount 4`; then `build.ps1`, then `capture.ps1 -NoBuild -Hygiene -CpuCount 4`.
  - A script change: the cases that execute the changed lines.
  - Performance token/marker/package changes: protocol host tests and the added smoke/Markers cases above; once per relevant change, trace capture with `-Perf boot`, malformed public arguments rejected before build, and debug/release daily-versus-perf packaging with kernel/module hashes and complete descriptor checks. Image-tool changes also run its host tests, fmt and clippy. Input/burn runtime acceptance belongs to later 0019c/d work.
  - Docs only: nothing to run.
- When the spec is complete, run the full `test.ps1` before the branch is merged.

## Coding conventions
- Every `unsafe` block has a `// SAFETY:` comment that says why its preconditions hold, and every `unsafe fn` documents its caller contract, normally under `# Safety`. Clippy enforces the comments in every crate: the root `Cargo.toml` denies `unsafe_op_in_unsafe_fn` and `clippy::undocumented_unsafe_blocks` in `[workspace.lints]`, and every member inherits that table; each `tools\` workspace repeats it. Never `allow` or `expect` either lint. The protocol crates, `mirror-acpi`, `mirror-ui-tokens`, `mirror-ext2-layout` and `tools\mirror-image` forbid `unsafe` with `#![forbid(unsafe_code)]`.
- Fail closed. Fully validate untrusted input before acting on it: ELF images, firmware tables, device descriptors, syscall arguments and the boot command line. Reject anything unknown or malformed, and bound every loop and wait.
  - Spec 0013 narrows this for firmware tables, which are still validated before use. A firmware habit costs only the record or table it affects: surplus CPU records and redundant or unmatched local NMI records in the MADT are dropped and counted in `MIRROR_ACPI_READY`, null and repeated root-table entries are skipped, an unreadable one is skipped with `MIRROR_ACPI_TABLE_SKIPPED`, and tables other than the MADT, HPET and FADT are not read past their signature; of the FADT only the header, Flags and reset register are read, and a bad one costs only the reset register (spec 0058a). HPET table fields that Mirror does not use are ignored. An IOAPIC ID register that disagrees with its MADT record is reported with `MIRROR_APIC_IOAPIC_ID`, not rejected.
- Roll back on failure. An operation that fails partway undoes its partial effects before it returns the error. A smoke test proves this, usually by comparing allocated frames before and after.
- DMA buffers have no `Drop`. Release them only after the device is reset or quiesced, and quarantine them if that fails. Report cleanup in markers such as `dma_reclaimed=1`.
- Never add serial output that carries user content (typed text, key codes, file or document data, pointer state), or a per-input marker, to a default build. Gate it behind `test-trace`, which `boot-smoke` implies. The one exception (ledger S7b) is the opt-in timing markers enabled by a valid `mirror.perf=` boot token (spec 0019); they carry no user content. Content-free lifecycle and device markers may print after user actions.
- Put test batteries and checks on test-fixture data behind `boot-smoke`, so a default build never panics on a test outcome or on disk contents.

## Serial markers
- The kernel reports results as single serial lines of the form `MIRROR_<AREA>_<EVENT> key=value ...`. In trace and smoke builds, userspace console output is escaped and prefixed with `user: `, so userspace cannot forge a marker; default builds print none of it.
- The marker-family checks in `scripts\common.ps1` (driver catalog, xHCI, USB, AHCI, clock, reset, PERF, crash) are closed-world:
  - an unknown name in a checked family fails the run;
  - each expected marker appears exactly once, with its full field list, in the checked order.
- The generic marker lists in `scripts\run.ps1` (`$markers`) and `scripts\capture.ps1` check presence only (capture also requires the init battery's markers to be absent). They miss duplicates, extra fields and order.
- `run.ps1` rejects a scenario-specific marker in every other scenario.
- So a new or changed marker needs the matching assertion change in the same commit. Values derived from other fields are recomputed in the script, never trusted as reported.

## Fault injection
Guest-side faults exist only in `boot-smoke` kernels. To add one:
1. Add a `mirror.test=<kebab-name>` token to `smoke_mode()` in `kernel\src\boot.rs`. Map it to a new `SmokeMode` variant, or to `SmokeMode::User(n)` for a probe that runs in `userspace\init` (raise init's `probe` bound in `userspace\init\src\main.rs`). Unknown or repeated tokens must still panic. `smoke_mode()` skips only the policy tokens `mirror.irq=pic`, `mirror.timer=pit` and `mirror.panic=halt|reboot`.
2. For a `User(n)` probe that faults, add its expected `(vector, error, cr2)` arm to `validate_process` in `kernel\src\userspace.rs`. Without it the boot panics with `unexpected probe`.
3. Add the PascalCase name to `-Fault` in `scripts\run.ps1`: both its `ValidateSet` and the `$testMode` switch. A `User(n)` probe also gets its number in the `$scenario` map and, unless it expects vector 14, an entry in the `$userVector` map. An expected fatal kernel fault joins `$fatalKernelFault` and gets its vector, and any nonzero error code, in the `$vector` and `$errorCode` maps of the fatal-diagnostic check. An expected panic joins `$panicFault`, and `Assert-MirrorCrash` in `scripts\common.ps1` gets its announced CPU and its panic message.
4. Assert the scenario's marker in that case, and reject the marker in every other case.
5. Add the case to `scripts\test.ps1`, which runs it in both build profiles, debug and release.
A passing smoke boot exits QEMU with code 33. An expected fatal fault or panic exits with 35, with an exact diagnostic and then the crash lines (spec 0051): the stop of the other CPUs, the backtrace, the crash screen (`drawn=1` and its readback with a display, `drawn=0` without) and the final action, which `Assert-MirrorCrash` checks on every smoke boot. A reset case (`-Fault Reset*`), and a panic case with `-PanicReboot`, end in a guest reset, which `-no-reboot` turns into exit code 0 (spec 0058a); `Assert-MirrorReset` checks the restart lines. Outside boot-smoke a crash halts in debug kernels and reboots after 10 s in release ones, unless `mirror.panic=halt|reboot` chooses. Host-side faults are QEMU options in `run.ps1`: blkdebug errors, removed devices, CPU models and CPU counts. The default smoke CPU, in `run.ps1` and `capture.ps1`, is `qemu64,+smep,+smap` (0016-D6).

`-Fault PerfInvalid` is a host-only raw-token test: it injects only `mirror.perf=bogus`, expects exactly `MIRROR_PERF_OFF reason=invalid` followed by the existing unknown-smoke panic and exit 35, and rejects public `-Perf`. The invalid performance token remains visible to the strict smoke parser and causes that panic; no separate `mirror.test=` token is injected. It adds no `SmokeMode` variant or production fault-injection path.
